# The portable ABI, dotnet64-v2

`dotnet64-v2` is the binary contract of portable mode: what an object compiled with `--runtime=portable` assumes, so that objects, archives and programs compiled by different llvmnet releases link and behave together. It is frozen at 1.0 ([ADR-09](../plan/decisions.md#adr-09-portable-abi-evolution)); an incompatible change needs a new tag (`dotnet64-v3`), which the linker keeps apart from v2. [modes.md](modes.md) describes portable mode as a whole; this page is the contract itself.

`tests/abi-freeze.sh` (core gate) enforces it: the header set, the data layout and the behavior of an object compiled when the ABI was frozen (`tests/abi/compat-object-v2.o`) must not change.

## What is frozen

| Part | Contract | Checked by |
| --- | --- | --- |
| Header set | The sysroot's installed headers, musl 1.2.5 and libc++ 22.1.8 with the llvmnet ports (`ports/musl`), identified by the stamp `sysroot/dotnet64-v2/.llvmnet-headers` (a SHA-256 over every header) | `tests/abi/dotnet64-v2.headers` |
| Target and data layout | LLVM target `x86_64-unknown-none` with x86-64's data layout: little-endian, 64-bit pointers, `long` and `size_t`; no x86 instruction set or host macros | `tests/abi/dotnet64-v2.layout` |
| Scalar types | `char` 8 bits (signed unless `-funsigned-char`), `short` 16, `int` 32, `long` and `long long` 64, `__int128` 128 with 16-byte alignment, `wchar_t` signed 32-bit, `int_fast16_t` and `int_fast32_t` 64-bit as in glibc | layout file |
| `long double` | x87 80-bit extended precision (64-bit significand, explicit integer bit) in 16 bytes with 16-byte alignment; computed in software on every host; the 10 bytes are stored and the padding is left as it was | layout file, compatibility object |
| Varargs | The System V `va_list`: one 24-byte record of `gp_offset`, `fp_offset`, `overflow_arg_area` and `reg_save_area`, laid out by the software varargs of [BE-19](../plan/01-compiler-backend.md) and independent of the host's calling convention | layout file, compatibility object |
| C library structures | musl's x86-64 layouts: `jmp_buf` and `sigjmp_buf` 200 bytes, `sigset_t` 128, `struct stat` 144, `struct sigaction` 152, `fpos_t` 16, pthread types as musl defines them, `BUFSIZ` 1024 | layout file |
| Signals and errno | Linux numbering (`SIGSEGV` 11, `ENOENT` 2, `ENOSYS` 38, `EOPNOTSUPP` 95 and the rest); musl's `strerror` texts | layout file |
| C++ | Itanium C++ ABI with libc++ ABI version 1 (`std::__1`); exceptions through libc++abi and the managed bridge ([dev/cxx-eh-bridge.md](../dev/cxx-eh-bridge.md)) | libc++ conformance (CX-08) |
| Fortran | Flang 22's descriptor (`CFI_cdesc_t`, CFI version 20240719) and flang-rt 22.1.8's entry points | flang-rt conformance (FT-06) |
| Host interface | The host functions musl's port calls and their Linux system-call semantics, listed in [dev/host-abi.md](../dev/host-abi.md); a host may refuse a service with the documented errno, but may not change the meaning of one it provides | host conformance (`tests/host.sh`) |
| Object format | LLVM bitcode carrying the module flag `llvmnet.abi = "dotnet64-v2"`, which `llvmnet -c` records and the linker checks | link tests |

The values the layout file pins are those a program can observe: `sizeof`, `alignof` and `offsetof` of the types above, the limits (`CHAR_MIN`, `WCHAR_MIN`, `LDBL_MANT_DIG`, `PATH_MAX` and others), signal numbers and errno values. The file is generated by `tests/abi/layout.c` and is readable as a reference.

## What is not part of it

- The managed surface of `--emit-library` beyond scalar and pointer `CExport` signatures; aggregate signatures may change ([linking.md](linking.md)).
- `LlvmNet.Runtime`'s internal methods and the CIL that llvmnet emits: images are compatible through the runtime's version check ([dev/versioning.md](../dev/versioning.md)), not through their IL.
- Performance, and the services a host cannot provide (they fail with the errors [limitations.md](limitations.md) lists).
- `--simd128` code: the `wasm_simd128.h` path is an opt-in profile on top of v2 ([simd128.md](simd128.md)).

## Changing it

A change that keeps every v2 object working (a header that gains a declaration, a host function that starts providing a refused service) updates the expected file in the same commit and says why. A change that would make an existing v2 object behave differently, or a v2 program see a different layout, needs `dotnet64-v3`: a new sysroot, a new tag in `PortableAbi.Tag`, the linker rejecting a mix of v2 and v3, and a new compatibility object. Changes that wait for v3 are recorded in [ADR-09](../plan/decisions.md#adr-09-portable-abi-evolution), such as the slot-array varargs layout (BE-19).
