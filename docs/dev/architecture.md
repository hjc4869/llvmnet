# Architecture

llvmnet translates linked LLVM bitcode to CIL. The same pipeline serves both runtime modes, `portable` (the default) and `system`; [user/modes.md](../user/modes.md) defines their ABI and deployment contracts.

## Pipeline

1. The driver (`src/LlvmNet.Compiler/Driver.cs`) runs clang-22 for C and C++ or flang-22 for Fortran and emits LLVM bitcode. The default is `-O1`; an explicit level overrides it and, as in Clang, `-O2` and above run the vectorizers (SV-05). The sysroot's build scripts pass `-fno-vectorize -fno-slp-vectorize`, so the runtime libraries stay scalar, as SV-05 measured them. Portable mode adds the sysroot's headers and a fixed target (`PortableAbi.cs`). Every object records its mode's ABI tag in the `llvmnet.abi` module flag.
2. A small C++ bridge to LLVM (`native/`, built as `libllvmnet-llvm.so`) links the bitcode with LLVM's linker, extracting archive members as a native linker does, and rejects inputs whose ABI tag differs from the link's. One `llvm::Linker` serves the whole link, because a linker indexes every struct type of its destination module when it is constructed (one per input made large links quadratic), and inputs are read lazily, so a function body is read only when its definition is linked. It also prepares modules for translation and builds the native call shims of system mode. It runs only inside the compiler.
3. Portable executables link musl's `crt1.o` and the sysroot archives (libomp, flang-rt, libc++, libc++abi, musl, compiler-rt builtins), extracting only the members the program uses; system executables link flang-rt from `sysroot/system-linux-x64-v1`.
4. `opt-22` runs the lowering passes. Executables internalize everything except the entry points and run global dead-code elimination; libraries keep their public definitions. Both scalarize masked memory intrinsics. Vector code stays whole for the typed vector lowering, reductions included, which expands and scalarizes the functions it does not translate in-process through LLVM's `expand-reductions` and scalarizer (`native/vectors.cpp`); the hidden `--vector-lowering=scalar` runs the scalarizer on everything instead, as before the lowering, and `--vector-lowering=typed` scalarizes only what the lowering does not translate.
5. The C# backend reads the module through LLVM's C API. LLVM's data layout determines sizes, alignments and structure offsets.
6. `PersistedAssemblyBuilder` emits static CIL methods into a PE image, which the .NET JIT executes. Functions are methods of a class `Program`; because the CLR allows at most 65,535 methods per type, internal methods beyond 32,768 go to further internal classes named `Program` in namespaces `LlvmNet.Methods<n>` (exports and the entry methods stay on `Program`), as static fields beyond 32,768 go to `__Statics<n>` classes.
7. `--nativeaot` publishes the emitted assembly with NativeAOT. System-mode native bridges become static native inputs, so the result is one executable.

## Values and Control Flow

LLVM SSA values map to typed CIL locals and basic blocks to CIL labels. PHI copies are evaluated before any destination is updated, preserving parallel assignment on every incoming edge.

Integers up to 32 bits use CIL `int32`, up to 64 bits `int64`, and up to 128 bits `UInt128` with explicit signed and unsigned helpers; wider integers are rejected. Narrow values are normalized to their LLVM bit width, and signed operations sign-extend from that width first. Odd-width stores touch only the bytes the LLVM value occupies.

Integer and pointer `select`, `llvm.abs` and the integer min/max intrinsics are computed with masks instead of branches (`false ^ ((true ^ false) & mask)`, `(x ^ s) - s`), because RyuJIT turns a branch into a conditional move only outside loops; a select whose condition orders two integers of at most 32 bits takes its mask from the sign of their 64-bit difference, and so do min/max of such integers. Min/max against a constant bound keep a branch: such clamps almost always go the same way, and a predicted branch costs less than a mask. Floating-point, 128-bit and aggregate selects keep a branch, which is exact for every value.

`float` and `double` use their CIL equivalents. `x86_fp80` uses `Float80`, a software value in 16-byte storage with a 64-bit significand, the full extended exponent range and round-to-nearest-even arithmetic; its constants are extracted bit for bit through LLVM. `half`, `bfloat` and `fp128` are rejected. `llvm.fmuladd` rounds the product and the sum separately, which LLVM permits, except in functions whose target features include FMA, where `llvmnet_fuse_multiply_adds` (native/vectors.cpp) makes it `llvm.fma` before the target attributes are removed, as native code fuses it there (SV-09); `llvm.fma` is fused. Integers wider than 128 bits that InstCombine makes of 256-bit vectors (a sub-vector taken with `lshr` and `trunc`, a comparison with zero) become shuffles, extracts and reductions (`llvmnet_narrow_vector_integers`).

Fixed-length vectors of 8- to 64-bit integers, pointers, `float`, `double` and `i1` are lowered to `Vector128<T>` operations (ADR-16 Level 1, `VectorEmitter.cs`), which RyuJIT and ILC compile to the host's SIMD instructions. A vector of at most 128 bits is one `Vector128<T>`, its unused upper lanes undefined (loads and stores touch exactly its store size: 8 bytes for `<2 x float>`, 12 for `<3 x i32>`); a wider one is a struct of 128-bit fragments, which RyuJIT keeps in separate registers. With `--vector-width=256` the fragments are `Vector256<T>`, for builds that target AVX2 hosts. Element-wise operations call the `Vector128<T>` operators, which RyuJIT expands itself, rather than `Vector128.Add` and its siblings, which reach the expansion only by inlining and stay calls in a method of about 920 locals. Integer lanes are signed and reinterpreted (`As`, free) where an operation needs another view; an `i1` vector is a mask of all-ones or zero lanes whose width follows from its lane count (16 lanes of 8 bits, 8 of 16, 4 of 32, 2 of 64), and a comparison whose own lanes have another width is computed again at its use instead of converted. Lane-width changes (`sext`, `trunc`, `fpext`, the conversions, masks) go through `Widen` and `Narrow`, `shufflevector` through constant `Shuffle`, a `Create` of halves (of 64-bit lanes within a `Vector128`, since x64 does not accelerate `Vector64`) or `ConditionalSelect` per result fragment, a chain of `insertelement`s at constant lanes through one `Create` of its lanes (without SSE4.1, `WithElement` of a 32-bit lane goes through memory), and what no vector instruction does (integer division, variable shifts, partial memory accesses, mask bits, bit counts and reversals as shift-and-mask compositions) through `LlvmNet.Runtime.Vectors`. `llvm.vector.reduce.*` is lowered directly: a power-of-two vector halves as `expand-reductions` and LLVM's backends do (an integer sum through `Vector128.Sum`), others go lane by lane, so `-O0` vector code, which skips `opt`'s passes, runs too. The generic intrinsics with a lowering are min and max, `abs`, saturating arithmetic, `ctpop`/`ctlz`/`cttz`, `bswap`, `bitreverse`, funnel shifts, the floating-point family and rounding, `fptosi.sat`/`fptoui.sat`, and `vector.reverse`/`insert`/`extract`. Parameters are typed vectors (x64 passes them on the stack, ARM64 in vector registers); a vector result of at most 16 bytes returns as its explicit-layout bytes, because .NET returns a `Vector128` through a hidden buffer, and NativeAOT does not make a `musttail` call through a function pointer with such a result a tail call.

Before translation, LLVM's scalarizer turns into scalar code every function whose vector code the lowering does not translate (lanes of no CIL vector type, such as `i24` or `i128`, vector `getelementptr`, vector intrinsics without a lowering) and every function whose vector code moves more lanes than it computes on: each lane inserted or extracted costs an instruction as a `Vector128` and none as scalars, and each operation on N lanes saves N - 1 scalar ones. That keeps vectorized loops as vector code and the x86-64 ABI's two-float `<2 x float>` and SROA's small arrays as scalar code. Vector values that remain in scalarized functions with lanes of no CIL vector type use explicit-layout value storage with lane insertion and extraction, including bit-packed integer masks. `llvmnet -v` names each scalarized function and why. Scalable vectors, target-specific intrinsics and some generic vector intrinsics are rejected; [user/support-matrix.md](../user/support-matrix.md) lists them.

In the functions that stay vector code, two widening reductions are recognized as LLVM's x86 backend recognizes them (SV-21, `llvmnet_widening_reductions` in `native/vectors.cpp`, after `X86PartialReduction`): where the tree of adds and phis that feeds an `llvm.vector.reduce.add` is read by nothing but the reduction, a leaf `abs(sub(zext a, zext b))` of bytes becomes `llvm.x86.sse2.psad.bw` and a leaf `mul(ext a, ext b)` of values that fit 16 signed bits `llvm.x86.sse2.pmadd.wd` (AVX2's forms for 32-byte chunks with `--vector-width=256`), which the x86 helpers run as the instruction where the host has it. Both leave other partial sums in the lanes than the literal code, which only the reduction's total could tell apart. Two leaves of one block whose operands fill half a fragment, as the 64-bit vectors of LLVM's x86 cost model do, share one instruction (the second becomes zero), so no lanes are spent on padding, which the AdvSimd and software compositions would compute too. The hidden `--vector-idioms=off` keeps the literal dataflow.

LLVM 22's scalarizer can corrupt the terminator of an `invoke` that returns a vector. Before scalarization, llvmnet wraps such results in a one-field aggregate and extracts the vector in a new normal-edge block, preserving PHI predecessors and the unwind edge.

The opt-in [SIMD128 path](../user/simd128.md) (`--simd128`, `--isa=wasm-simd128`) is a header on the typed lowering: `wasm_simd128.h` writes most intrinsics as vector extensions, and the operations Clang's header takes from `llvm.wasm.*` intrinsics call `__llvmnet_simd128_*` helpers that take and return `Vector128<byte>`. A call to a runtime method reinterprets a vector argument or result of the same width with other lanes (`Vector128.As`, free; `CilCompiler.Reinterpretable`), since the header's vector types differ from the helpers'.

x86 target intrinsics (ADR-16 Level 2, [x86-intrinsics.md](../user/x86-intrinsics.md)) are runtime methods marked `[LlvmIntrinsic("llvm.x86....")]` in `LlvmNet.Runtime.X86`; `TargetIntrinsics` collects them by name, and a call of one loads its operands, converts each vector to the helper's lanes (with `--vector-width=256`, the low half of a `Vector256` to `Vector128` and back) and calls the helper, which the JIT and ILC inline. An immediate operand stays the call's constant, so after inlining `Sse41.DotProduct` and its siblings get their immediate form; a helper left as a call takes .NET's jump table. Each helper branches on `IsSupported` for the x86 instruction (a constant for the JIT, a run-time test for ILC's opportunistic sets), then for the AdvSimd one, and composes the result from `Vector128` operations otherwise. A function that calls one stays vector code (`VectorEmitter.Unsupported` accepts the table's names). The level a unit was compiled for (`--isa`) is the object's `llvmnet.isa` module flag (`AppendUnique`, so objects of all levels link); the driver gives a NativeAOT program with `x86-64-v2` objects ILC's `x86-64-v2` instruction set.

CPU detection (SV-12): `FunctionEmitter.CpuQuery` recognizes CPUID and XGETBV inline assembly by its normalized text and constraints; system mode calls a generated native thunk, portable mode `CpuFeatures.CpuId` and `XGetBv`, which write the registers into the asm's result structure (X86Base.CpuId on x64, zeros elsewhere, XCR0 from CPUID leaf 0xD with the AVX components only where .NET uses them). compiler-rt's `cpu_model/x86.c` is in both sysroots' `libclang_rt.builtins.a`, so `__cpu_model` and `__cpu_indicator_init` (an `int` constructor, whose result the constructor runner drops) come from its own CPUID queries. The linker lowers GNU ifuncs with LLVM's `lowerGlobalIFuncUsersAsGlobalCtor`, naming the table and the priority-10 constructor it creates, only for modules that have them. `ProcessRuntime` adds `AT_HWCAP` and `AT_HWCAP2` to musl's auxiliary vector.

Native kernel packages (SV-13, [native-kernels.md](../user/native-kernels.md)): `KernelPackage` reads `--native-kernels` manifests, and `CilCompiler.ResolveFunction` asks `KernelStubs` for a declaration a package lists before reporting it unresolved. Each kernel gets a wrapper with the declaration's managed signature (`AggressiveInlining` and `AggressiveOptimization`), which extends narrow arguments per `signext`/`zeroext` and calls one of two P/Invokes chosen by `RuntimeFeature.IsDynamicCodeCompiled`: `llvmnet-kernel:<package>:<symbol>` under the JIT, bound at its first call by `NativeKernels`' `DllImportResolver` from `runtimes/<rid>/native/`, and the package's library as NativeAOT, `SuppressGCTransition` for leaf kernels and bound by `DirectPInvoke` to the static library the project links per runtime identifier. The JIT's import keeps the GC transition, because a transition-free P/Invoke is bound whenever the JIT compiles a caller; the wrapper is optimized from the start because tier 0 keeps the NativeAOT branch. The JIT folds the test only once `RuntimeFeature` is initialized (its getter reads a static read-only field), which `NativeKernels.Register` does in the image's initializer; the data accessors, which that initializer calls, are therefore not inlined. An optional kernel's wrapper first asks `NativeKernels.IsAvailable` and returns where the host has no library. A global the manifest's `data` lists is allocated in `EmitInitializer` from the package's accessor stub (`llvmnet_kernel_data_<name>`) where the package is available, so the C initializer that follows fills the library's copy; the driver keeps those globals external and linked (`--internalize-public-api-list`, required link roots), and `native/linker.cpp` skips archives' native object members when the link has packages. The hidden `--print-kernel-data=<file>` links the inputs and prints, instead of compiling, the C storage and accessors that `scripts/kernels.py` builds into the libraries.

System mode's native objects (SV-15, [linking.md](../user/linking.md#native-objects-and-assembly-system-mode)): the driver assembles `.s`/`.S` with Clang and `.asm` with nasm, recognizes native objects by content (`Driver.IsNativeObject`) and has `native/objects.cpp` (`llvmnet_native_objects`) list their symbols and extract archives' native members, which the bitcode linker skips in system mode. Their references are required link roots and stay external. `HostInterop.ClassifyObjects` rejects calls into the program and undefined symbols, `HostInterop.Direct` gives scalar kernels a `musttail` forwarder in the shim (`llvmnet_add_native_forwarder`) and a transition-free P/Invoke behind an inlined wrapper, and `HostInterop.DataAccessor` places the shared data in the native library, whose `Build` links the objects, the shim and `Driver.KernelDataSource`'s C with `-Bsymbolic`, or archives them for NativeAOT.

## Memory and Calls

Pointers are native integers into unmanaged memory. Globals and constant aggregates are allocated before their initializers and relocations are installed. Large initialized globals are embedded in data fields of at most 1 MiB and copied into one contiguous allocation before relocations are applied. Function pointers use `ldftn`, and calls to translated targets use `calli`.

Arrays and structures are explicit-layout value types used as bit containers. Loads and stores use unaligned-safe CIL or exact-width helpers. Allocas use aligned stack allocation; functions with stack save/restore or nonlocal-jump sites use scoped aligned allocations that are released on restore or unwind. `byval` parameters receive a private aligned copy, and hidden `sret` pointers are preserved.

In functions of more than 512 values, values of one CIL type share an IL local when their live ranges do not meet (`FunctionEmitter.ShareFunctionLocals`, BE-33): a range spans, in emission order, the value's definition, its uses and the blocks it is live into or out of, and an instruction's result never shares its operands' locals. RyuJIT keeps at most 1,024 locals of a method in registers and stops inlining from about 920, which a local per value put out of reach of any function of a thousand instructions; smaller functions keep a local per value, because RyuJIT allocates registers per local and sharing costs moves in small loops. Functions with `setjmp` sites keep a local per value, because the jump dispatch re-enters the body. Functions with more than 32,768 SSA values and no `setjmp` sites reuse primitive locals whose uses stay within one block, and keep values that cross blocks in typed per-call arrays, so they stay below the CIL local limit. Large aggregate-heavy or `setjmp` functions can still exceed CLR limits; `--diagnose-limits` reports the sizes.

Direct `setjmp` sites resume through a managed exception dispatcher in the owning activation, preserving live locals and restoring allocation checkpoints. `longjmp` cannot cross native frames. `sigsetjmp` saves the requested signal mask: the native one in system mode, the host layer's in portable mode.

A `musttail` call becomes a CIL `tail.` call followed by `ret`. The JIT honors it as a fast tail call that reuses the frame or, when it cannot, through the runtime's tail-call helpers; NativeAOT has no helpers, and on x64 refuses a fast tail call from a method that uses `localloc`. A function with a `musttail` call therefore takes its allocas and variadic call area from the scoped allocation arena, and a tail call inside the arena's (or a `setjmp` dispatcher's) protected region first leaves it, so the `finally` releases the arena before the call. Calls a fast tail call cannot carry are compile errors: `byval` arguments, arguments or results of more than 16 bytes, and forwarded variadic arguments. Windows x64 passes 16-byte values by reference too, so there NativeAOT makes a `musttail` call with a vector, `long double` or 128-bit argument an ordinary call. Ordinary `tail` calls are plain calls: an explicit tail call is never inlined.

Defined thread-local globals use lazy per-thread storage with initialization and destructor cleanup. External thread-local globals need a bitcode definition.

Variadic calls build a software x86-64 SysV register-save and overflow area, and translated `va_start`, `va_copy` and `va_arg` sequences, including musl's `printf` family, read the same layout. Aggregates passed to variadic functions follow the System V classification: one register slot per eightbyte of a small struct when they all fit, otherwise the overflow area, where `byval` arguments and `long double` also go.

C calls without a prototype may use a variadic LLVM signature for a fixed-arity definition. Direct calls then use the definition when the required argument types match, drop unused trailing arguments such as Fortran hidden character lengths, and discard an unused result. Direct calls also follow x86-64's register-slot rules: `i32` and `i64`, `ptr` and `i64`, and `i1` and `i8` are interchangeable in register positions. Other signature mismatches are compile errors. Missing required arguments are compile errors unless `--trap-missing-arguments` turns the call site into an exception; a call without arguments through a prototype without parameters, the shape of configure probes, always becomes one, with a warning. [dev/calling-convention.md](calling-convention.md) gives the full rules.

In system mode, translated callbacks passed to native code get unmanaged-callable entry points registered against their managed implementations, and indirect calls through those pointers resolve back to the managed method. Native variadic functions are called through LLVM-generated thunks with the call site's signature. Native calls into translated variadic or aggregate callbacks fail with a diagnostic.

## Runtime

`LlvmNet.Runtime` is a .NET assembly copied next to every output. Its public static methods marked with `CExportAttribute` resolve C symbols; the compiler checks them against the LLVM signatures. It contains:

- The host layer (`Host/`, portable mode): the Linux system calls musl issues, implemented over .NET for files, the file system, memory mappings, processes and signals, threads (musl's `clone` on managed threads, futexes) and time. [dev/host-abi.md](host-abi.md) is its contract.
- Compiler helpers: atomics, `Float80`, wide integers, math intrinsics, varargs, stack allocation, nonlocal jumps, thread-local storage, vector lanes (`Vectors`), SIMD128, x86 intrinsics (`X86`) and `--check-indirect-calls`.
- The C++ exception bridge (`Cxx.cs`, [dev/cxx-eh-bridge.md](cxx-eh-bridge.md)).
- System-mode adapters: native callbacks, `pthread_create` and key destructors, and `atexit`/`exit` ordering.

Atomics on naturally aligned 8- to 64-bit locations use `Interlocked` and `Volatile`, so they are lock-free and interoperate with native atomics in system mode. Misaligned locations take a lock, and 128-bit atomics use a lock striped by address.

In portable mode, musl's pthreads run on managed threads, with the thread pointer and futexes provided by the host layer. In system mode, threads are native pthreads; an adapter wraps thread start and TLS destructors so that callbacks run inside .NET's thread lifetime. Neither mode reproduces native asynchronous signal delivery into arbitrary code; [dev/host-abi.md](host-abi.md) describes how portable mode delivers signals.

C++ `invoke` becomes a CIL try/catch region. Landing pads select matching C++ types and exception-specification filters, and resume or rethrow propagates a managed exception that carries the C++ object. In portable mode, catch matching, `type_info` and `dynamic_cast` come from libc++abi; in system mode the bridge implements them, and the optional libstdc++ archive (see [user/modes.md](../user/modes.md#optional-system-c-library)) supplies the library.

Fortran uses Flang 22 CFI descriptors and flang-rt in both modes: compiled against musl and libc++ in the portable sysroot, and against glibc in the system sysroot. System-mode OpenMP links LLVM's native `libomp`; outlined regions remain translated CIL and enter through native-callable thunks, and Flang's host `DO CONCURRENT` lowering uses the same path. Portable mode links LLVM's OpenMP runtime (libomp) from the sysroot, built on musl's pthreads with the port in `ports/openmp`; outlined regions are ordinary translated functions the runtime calls through its C invoker.

## Linking Boundaries

- LLVM bitcode linking is static and uses `-L`/`-l` or explicit object and archive paths.
- Managed linking uses `--cil-reference` and `CExport` methods.
- System mode resolves the remaining symbols in native libraries (the C library and `--system-library`) through generated LLVM bridges and unmanaged-callable callbacks.

Portable mode accepts only the first two: native libraries are rejected. A native extension ([user/extensions.md](../user/extensions.md)) is the second kind: a generated managed reference whose stubs call a host library they load at run time, registered with the runtime's `dlopen` at start.
