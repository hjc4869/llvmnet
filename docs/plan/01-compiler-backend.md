# Workstream BE: Compiler backend (LLVM IR to CIL)

Prefix `BE`. Owner: unassigned. Primary milestone: [M1](README.md#m1-backend-hardening); several items are prerequisites for the library spikes in M2.

The backend is the part of llvmnet that must be kept. This workstream makes it provably correct for the IR that real libraries (musl, libc++, flang-rt, ffmpeg, SPEC) produce, makes failures diagnosable, and removes the structural obstacles to maintaining it.

## Current state (verified 2026-10-30)

- About 3,500 lines of C# in `src/LlvmNet.Compiler` across 12 files. `FunctionEmitter.cs` is 1,516 lines; `Instruction` (about 180 lines), `Call` (about 200) and `Intrinsic` (about 445) are single methods with large switches. `ValueEmitter` owns loads/stores/casts/GEP, `CilCompiler` drives module emission with `PersistedAssemblyBuilder` and patches `calli` signature tokens into the finished PE image.
- LLVM is reached through `DllImport("libLLVM-22.so")` plus a 271-line C++ bridge (`native/*.cpp`, built as `libllvmnet-llvm.so`) for linking, ABI stamping, native shims, vector-invoke wrapping and exact constant extraction. The LLVM major version is hard-wired in library names and `-22` tool suffixes.
- Legalization runs as `opt-22` passes (`internalize`, `globaldce`, `expand-reductions`, `scalarizer`) before emission.
- 29 `llvm.*` intrinsic families are recognized; unrecognized ones raise `NotSupportedException` (134 such throw sites in the compiler and runtime). There is no machine-readable support matrix.
- Atomics are implemented with one process-wide lock (`Atomics.gate`) for every width and address. Correct, but every atomic in a threaded program serializes on it.
- Allocas use `localloc`, or a heap-backed `StackMemory` list when the function has stack save/restore or nonlocal jumps. `byval` arguments are copied per call.
- Debug metadata is discarded (`llvm.dbg.*` ignored, `-g` forwarded to Clang only). Stack traces show `Program.<llvm-name>` and no source lines. Diagnostics are exception messages without file/line; `LLVMNET_TRACE=1` adds a .NET stack trace.
- Known unsupported (from `docs/user/limitations.md`): computed goto / `indirectbr`, cross-native-frame `longjmp`, external native TLS, scalable vectors, masked memory intrinsics, `fp128`, some wide-integer intrinsic families, inline assembly beyond an allowlist, and methods that exceed CLR local limits.
- The core gate, driver test and smoke test pass on the current host.

### Found while measuring (M1)

- [ ] **BE-33** (L, P1) Emit denser IL and reuse locals across blocks. `--diagnose-limits` shows the hottest ffmpeg, perlbench and gcc functions expand to about 21 IL bytes per LLVM instruction with thousands of locals, putting them past RyuJIT's MinOpts thresholds (38 ffmpeg, 23 perlbench and 40 gcc methods). Target: halve IL bytes per instruction and keep the measured hot functions below the thresholds; complements BE-26. — **Locals shared, IL density open** (2026-11-04, [evidence](../evidence/2026-11-04-be33-local-sharing.md)): in functions of more than 512 values, values of one CIL type share a local when their live ranges, from a liveness pass over the function, do not meet (smaller functions keep a local per value: RyuJIT allocates registers per local, and sharing cost small loops moves), which leaves every ffmpeg method far below the 2,000-locals threshold (`ff_h264_decode_mb_cabac`: 97 locals from 6,505) and shrinks the decoder's IL by a fifth (22.99 to 18.24 MB, short-form local indices). Found by SV-05: RyuJIT tracks only 1,024 locals and stops inlining from about 920, so a function of a thousand instructions and more ran with its values in memory (musl's `printf_core` had 1,421 locals; Stepanov's vectorized `main`, 1,499, ran 7 times slower than its scalar build). Methods past a MinOpts threshold in the decoder: 16 from 38, all on IL size; halving IL bytes per instruction is still open.
- [ ] **BE-34** (M, P2) Constrained floating point with static non-nearest rounding modes and observable exception flags; today such calls are rejected, while to-nearest and dynamic ones are lowered to plain operations.

### Found by fuzzing (FD-16)

- [x] **BE-35** (S, P0) Globals beyond 2 GB. Constant data was collected in one array, so a global over 2 GB, such as YARPGen's multidimensional arrays, failed with an internal overflow error (19 of 400 programs), and every global was cleared page by page at startup. — **Done** (`7a607d2`): sparse 1 MB constant chunks; globals use lazily zeroed memory like ELF `.bss` (`tests/c/huge-globals.c`, 5 GB of globals in 36 MB of memory).
- [ ] **BE-36** (M, P1) Integers wider than 128 bits. - [x] **BE-37** (S, P1) The remaining `x86_fp80` intrinsics (`llvm.pow`, `log10`, `minimum`, `maximum`, `canonicalize` and others listed as rejected in `docs/user/support-matrix.md`); `copysign`, `maxnum` and `minnum` were added when musl and compiler-rt needed them. - [ ] **BE-38** (M, P2) Half-precision (`half`, Fortran `REAL(2)`) constants and arithmetic, rejected today ("Unsupported floating constant: half"); found by the gfortran conformance run.
- [x] **BE-39** (S, P2) Decide whether portable mode adopts system mode's scalar register-slot rules for direct calls (BE-18): Flang with `-fdefault-integer-8` declares `_FortranAProgramStart` with a 64-bit argument count, and C interoperability passes hidden character lengths as `i64` where C takes `int`. - [x] **BE-40** (S, P2) Scalars passed or returned as one-element arrays: Fortran interoperability passes `character(1)` by value as `[1 x i8]` where C takes `char`, and returns it the same way (6 gfortran conformance tests, both modes). x86-64 passes a one-element array in the element's register, so the two are interchangeable at direct calls; llvmnet rejects the mismatch. — **Done** (this commit): direct calls convert between `i8` and `[1 x i8]` arguments and returns in both modes, through a one-byte temporary; C's `signext` on such a parameter is accepted, since the callee extends the byte itself (`tests/ir/system/legacy-register-width.ll`). 4 of the 6 tests pass; the other 2 also omit the hidden length argument a Fortran callee declares, which stays a compile error.

### Found by the library survey (2026-11-02)

Measurements and reproducers: [library survey](../evidence/2026-11-02-library-survey.md).

- [x] **BE-44** (M, P0) `musttail` calls are translated as ordinary calls, without a diagnostic, so a chain of tail calls that runs in constant stack natively overflows (the JIT reports a stack overflow, NativeAOT dies with SIGSEGV). Skia's SkSL raster pipeline relies on it, and its DM test runner aborts after 2,017 of 2,197 tests. Guarantee the tail call (a CIL `tail.` prefix where the JIT and NativeAOT honor it, or a trampoline) or reject `musttail` with a compile error listed in the support matrix. Done when the reproducer runs in constant stack under the JIT and NativeAOT, or fails to compile with the diagnostic. — **Done** (2026-11-02, `8ff348b`): a `musttail` call becomes a CIL `tail.` call followed by `ret`. A function that makes one takes its allocas and variadic call area from the per-thread arena instead of `localloc`, so NativeAOT can make a fast tail call; what a fast tail call cannot carry (`byval` arguments, arguments or results over 16 bytes, forwarded variadic arguments) is a compile error listed in the support matrix, and on Windows x64 a NativeAOT call with a 16-byte argument stays an ordinary call. The reproducer, which overflowed before, runs 1,000,000 and 100,000,000 calls in constant stack under the JIT and NativeAOT. Evidence: [2026-11-02-musttail-select.md](../evidence/2026-11-02-musttail-select.md).
- [ ] **BE-45** (M, P1) `setjmp` called through `invoke`: inside a C++ `try`, Clang emits `invoke @setjmp` because musl's `setjmp` is not `nothrow`, and llvmnet rejects it ("setjmp requires a direct call"); LibRaw's `unpack_thumb` does this. Done when the reproducer compiles and behaves as native under the JIT and NativeAOT.
- [ ] **BE-46** (S, P1) `--diagnose-limits` models IL size, blocks, locals and LLVM instructions but not RyuJIT's other MinOpts triggers, so `hb_ot_tags_from_script_and_language` (52.9 KB of IL, 1,406 locals) is reported under every threshold while the JIT compiles it as MinOpts (4 times slower than native). ### Found by building LLVM with llvmnet (2026-11-02)

- [x] **BE-47** (S, P0) A program with more than 65,535 methods does not load: every function became a method of the one `Program` class, and CoreCLR refuses such a type ("Type 'Program' ... contains more methods than the current implementation allows") when the program starts, after a successful link. Clang built with llvmnet has 119,681 methods and Flang 234,651; in system mode each address-taken function adds a callback entry point. Done: internal methods (translated functions, thread-local getters, system mode's host wrappers and callback entry points) beyond 32,768 per class go to further internal classes named `Program` in namespaces `LlvmNet.Methods<n>`, as static fields already go to `__Statics<n>`; they are internal instead of private so they call one another across classes, and exports and the entry methods stay on `Program`, whose type initializer runs before any of them. `tests/many-functions.sh` runs a 70,000-function program in both modes and a library of that size entered through its export, which master could not load; llvmnet-built Clang and Flang run. Evidence: [2026-11-02-method-holders.md](../evidence/2026-11-02-method-holders.md).

## Exit criteria for M1

BE-04, BE-05, BE-07, BE-08, BE-11, BE-12, BE-15, BE-16, BE-18, BE-25 and BE-31 are done; the fuzzing job (FD-16) has run for two weeks without an open miscompile; the support matrix (BE-02) is published.
