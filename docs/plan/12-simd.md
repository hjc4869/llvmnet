# Workstream SV: SIMD and vector code

Prefix `SV`. Owner: unassigned. Milestone: [M11](README.md#milestones), before 1.0 by the owner's decision of 2026-11-03 ([ADR-10](decisions.md#adr-10-simd-strategy) keeps scalarization for 1.0). The decision this workstream depends on is [ADR-16](decisions.md#adr-16-simd-levels), which breaks the "general vector lowering" that ADR-10 deferred (BE-32, PF-09) into levels that can ship one at a time.

Vector code reaches llvmnet in four forms: LLVM's own vectorizers (off by default, ADR-11), GCC vector extensions in C and C++ (Skia's `skvx`, SIMDe's fallbacks), CPU intrinsics (`<immintrin.h>`, `<arm_neon.h>`, `<wasm_simd128.h>`) and assembly, inline or in separate `.asm`/`.S` files. Today every form but the opt-in `wasm_simd128.h` subset runs as scalar CIL or is rejected, and the library survey measured the price: Skia's 8-lane kernels at 30 to 80 times native, the shipped dav1d and libjxl 10 to 17 times faster than llvmnet's scalar builds ([evidence](../evidence/2026-11-02-library-survey.md)). This workstream gives each form a path to the host's SIMD units while the portable image stays one file for every host: **Level 1** lowers LLVM vector IR to `Vector128<T>` and `Vector256<T>`, **Level 2** translates the target intrinsics of x86, WebAssembly and NEON through helpers that pick the host's instruction at JIT or AOT time, **Level 3** bundles natively assembled kernels per runtime identifier with the program's own C fallback, and **Level 4** (experimental) lets llvmnet compile leaf functions natively itself. The levels are independent deliverables; each one's exit is a measured gain on real code and no regression anywhere else.

## Current state (verified 2026-11-03)

- `opt-22` runs `expand-reductions`, `scalarize-masked-mem-intrin` and `scalarizer<load-store>` before translation ([Driver.cs](../../src/LlvmNet.Compiler/Driver.cs)); vector values that survive (function boundaries, PHIs the scalarizer leaves) use explicit-layout value types with lane insertion and extraction ([architecture.md](../dev/architecture.md#values-and-control-flow)). `--simd128` keeps 128-bit loads and stores whole as `Vector128<byte>` and lowers 46 `__llvmnet_simd128_*` helper calls declared by [sysroot/simd128/include/wasm_simd128.h](../../sysroot/simd128/include/wasm_simd128.h) to [Simd128.cs](../../src/LlvmNet.Runtime/Simd128.cs) ([simd128.md](../user/simd128.md)).
- Target intrinsics are rejected: every `llvm.x86.*` but `_mm_pause` and the three fences (SA-12 added the compile-time warning and the link-time message), all `llvm.aarch64.*` and `llvm.wasm.*`. Inline assembly is rejected beyond the allowlist (empty barriers, tied outputs, `int3`, and in system mode CPUID and XGETBV through native thunks). `ifunc` resolvers (`target_clones`) are rejected, and `__builtin_cpu_supports` does not link in either mode: `__cpu_model` is unresolved, because the portable builtins archive has no `cpu_model` member and system mode's bridge finds the symbol in no library.
- The vectorizers are off by default (`-O1 -fno-vectorize -fno-slp-vectorize`, ADR-11); `tests/vector-sweep.sh` checks that `-O3 -fvectorize` output is correct, not fast. For the portable target the loop vectorizer emits `<4 x i32>`, `<4 x float>`, `<2 x double>` and the SLP vectorizer `<2 x i32>`, `<2 x float>`, `<3 x i32>`; with AVX2 features the loop vectorizer emits `<8 x i32>` and `<16 x i32>` and masked stores ([evidence](../evidence/2026-11-03-simd-survey.md#what-the-vectorizers-emit)).
- The survey corpus is SIMD-heavy in every form: ffmpeg has 185 nasm files for x86 and 66 `.S` files for AArch64, dav1d 47 and 43, libjpeg-turbo 91 nasm files and 15 NEON intrinsic files; libjxl, Opus, libwebp, Skia, brotli and zlib use x86 and NEON intrinsics; Skia's `skvx` and libjxl use GCC vector extensions; 15 ffmpeg files and 7 dav1d files detect the CPU ([census](../evidence/2026-11-03-simd-survey.md#simd-and-assembly-census-of-the-survey-corpus)).
- Of 99 common SSE2 to AVX2 intrinsics, Clang lowers 53 to generic vector IR (which Level 1 covers with no table) and 46 to `llvm.x86.*` target intrinsics: the saturating packs, `psadbw`, `pmaddwd`, `pmaddubsw`, `pmulhw`, `pmulhrsw`, `pavgb`, `pshufb`, `phadd`, `psign`, shifts by a vector count, `blendv`, `ptest`, `dpps`, `phminposuw`, `mpsadbw`, `cvtps2dq`/`cvttps2dq`, `minps`/`maxps` (NaN rules), `rcpps`/`rsqrtps`, `comiss`, `cvtss2si`, `crc32`, and AVX2's gathers, `permd`, `psllv` ([classification](../evidence/2026-11-03-simd-survey.md#which-intrinsics-clang-lowers-to-generic-ir)). LLVM 22 defines 328 x86 intrinsics from SSE through AVX2 and FMA, 723 for AVX-512, 209 NEON and 25 WebAssembly SIMD intrinsics.
- .NET 10 on this host: `Vector128`, `Vector256` and `Vector512` are hardware accelerated under the JIT, `Vector64` is not on x64 (an add costs about twice a `Vector128` add); the ISA classes cover SSE through AVX-512, AVX10, NEON, SVE (not yet usable at run time) and wasm `PackedSimd`. NativeAOT's default instruction set reports SSSE3, SSE4.1, SSE4.2 and POPCNT as supported (opportunistically, through a runtime check) but not AVX; `--aot-instruction-set x86-64-v3` adds AVX2, FMA and BMI2 and makes `Vector256` accelerated. An opportunistic set only helps IL that checks `IsSupported` itself: `Vector128.Shuffle` with run-time indices costs 13 ns at the default level and 4 ns through an explicit `Ssse3.IsSupported` branch, on the same CPU ([measurements](../evidence/2026-11-03-simd-survey.md#net-simd-surface-and-nativeaot-instruction-sets)).
- `scalarizer<min-bits=128>` splits wider vector operations into 128-bit fragments instead of scalars, which is the legalization Level 1 needs; it leaves shuffles and reductions whole, and `expand-reductions` turns a reduction into a shuffle tree first ([evidence](../evidence/2026-11-03-simd-survey.md#legalizing-wide-vectors-with-llvms-scalarizer)).
- Hand-written `Vector128` loops shaped like LLVM's SSE2 output, the stand-in for Level 1, run 3.7 to 5x faster than today's scalar translation on element-wise and widening kernels and 2.3 to 3.9x on float dot products, with `Vector256` about double that on an AVX2 host; the neutral API is level with native SSE2 (0.76 to 1.01x) except on the widening reductions `psadbw` and `pmaddwd` (1.36 to 1.58x), which the x86 intrinsics behind `IsSupported` close; today's scalarized `-O3 -fvectorize` output costs 1.2 to 2x over `-O2`. Two scalar findings came out of it: translated code reloads every global's base address on each access (PF-17) and the branch-free select makes a loop-carried maximum 7x native (PF-18) ([measurements](../evidence/2026-11-03-simd-survey.md#hand-written-vectors-against-scalar-and-native-code)).

## Design

### Terms

- **Vector width**: the bits of a vector value in CIL, 128 (`Vector128<T>`, every host) or 256 (`Vector256<T>`, accelerated where the host has AVX2; two 128-bit halves elsewhere). 64-bit and odd LLVM vectors are widened to 128 bits; wider ones are fragmented or, with `--vector-width=256`, kept.
- **ISA level**: what the frontend may assume for intrinsics, macros and vectorization: `baseline` (today's portable target, SSE2-equivalent 128-bit operations, no x86 macros), `x86-64-v2`, `x86-64-v3`, `wasm-simd128`, `neon`. It changes no data layout; the data ABI stays `dotnet64-v2`.
- **Helper**: a static method of `LlvmNet.Runtime` that implements one target intrinsic, with an explicit `IsSupported` branch per host instruction set and a `Vector128` composition as the fallback.
- **Kernel package**: a directory of natively assembled or compiled code (one shared and one static library per runtime identifier) with a manifest listing its symbols; the program calls its functions through compiler-generated stubs and keeps its own C fallback.
- **Fragment**: a 128-bit piece of a wider vector operation after legalization.

### The levels

| Level | Input | Output | Hosts | Items |
| --- | --- | --- | --- | --- |
| 0 (today) | any vector IR | scalar CIL; `wasm_simd128.h` subset to `Vector128` helpers | all | done |
| 1 | LLVM vector instructions and generic vector intrinsics, from the vectorizers, vector extensions or the half of the x86 intrinsics Clang lowers generically | typed `Vector128<T>` / `Vector256<T>` CIL | all; the JIT and ILC pick the instructions | SV-02 to SV-07 |
| 2 | `llvm.x86.*` (SSE to AVX2, FMA), `llvm.wasm.*`, `llvm.aarch64.neon.*` | calls to inlinable helpers with `IsSupported` dispatch and portable fallbacks; the `--isa` option selects the headers and macros | all; fast paths where the host has the instruction | SV-08 to SV-11 |
| 3 | `.asm`/`.S` kernels and natively compiled objects, assembled per runtime identifier by the project's build | stubs that call the kernel library of the running host (JIT) or the statically linked archive (NativeAOT), with the project's C fallback where no library exists; CPU detection APIs | the identifiers the package provides; C elsewhere | SV-12 to SV-16 |
| 4 (experimental) | leaf functions with intrinsics or inline assembly that no earlier level accepts | the same functions compiled natively by LLVM's backends: into the system-mode sidecar, or per-identifier packages for portable images, with the CIL translation as fallback | as Level 3 | SV-17, SV-18 |

A program may use any mix. The baseline stays what it is today: a library that targets one ISA per compile (x86 intrinsics and nasm under `__x86_64__`) builds with `--isa=x86-64-v2` or `-v3` and, if it ships assembly, a kernel package for the identifiers its build produced; every other host runs its C paths. Nothing requires changing the library's dispatch; the extended detection APIs (SV-12) and multi-ISA bundles (SV-16) are opt-in.

### Level 1: general vector lowering

Types. An LLVM vector `<N x T>` whose element is `i8`, `i16`, `i32`, `i64`, `float` or `double` maps by total width:

| LLVM type (examples) | CIL type | Rule |
| --- | --- | --- |
| `<4 x i32>`, `<16 x i8>`, `<2 x double>` | `Vector128<int>`, `Vector128<byte>`, `Vector128<double>` | exactly 128 bits: direct |
| `<2 x i32>`, `<4 x i16>`, `<2 x float>`, `<3 x i32>`, `<3 x float>` | `Vector128<T>` with unused upper lanes | under 128 bits: widened; loads and stores touch exactly the LLVM allocation size (8 bytes for 64-bit vectors, 16 for `<3 x float>`, whose alloc size is 16); `Vector64<T>` is not used because x64 has no hardware path for it |
| `<8 x i32>`, `<16 x float>`, `<32 x i8>` | fragments of `Vector128<T>`, or `Vector256<T>` with `--vector-width=256` | over 128 bits: the backend splits every operation into fragments itself, a struct of `Vector128<T>` fields holding the value (as built in SV-02: `scalarizer<min-bits=128>` leaves comparisons and selects whole, because their `i1` results do not split at 128 bits) |
| `<N x i1>` | `Vector128<T>` mask of the lane width its producer or consumer uses (all bits set per lane), or an integer when it feeds `bitcast` to `iN` | masks have no memory form of their own; `zext <N x i1>` is `and 1`, `bitcast <16 x i1> to i16` is `ExtractMostSignificantBits`, a mask used at another lane width is widened or narrowed at the use |
| `<2 x ptr>`, `<4 x ptr>` | `Vector128<long>` | pointers are 64-bit lanes |
| `<N x i128>`, `<N x x86_fp80>`, lanes narrower than 8 bits other than `i1`, scalable vectors | scalarized as today or rejected with the type's name | no CIL vector type has such lanes |

Instructions. Arithmetic and logic are the `Vector128` operators; `icmp`/`fcmp` are `Equals`, `GreaterThan` and the other comparison methods, with the unordered predicates composed from `IsNaN`; `select` on a vector condition is `ConditionalSelect`; `shufflevector` with a constant mask is classified (identity, splat, concatenation of halves, interleave, half extraction, reverse, rotate, single-source byte permutation, two-source) and emitted as `GetLower`/`GetUpper`/`Create`, `WidenLower`-style interleaves, or `Shuffle` with constant indices, which RyuJIT turns into the exact instruction; `insertelement`/`extractelement` with constant indices are `WithElement`/`GetElement` and with variable indices go through memory; casts are `Widen`/`Narrow` (with the sign and truncation rules of `zext`/`sext`/`trunc`), `ConvertToInt32`/`ConvertToSingle` and their siblings (`fptosi` out of range is poison in LLVM, so .NET's saturation is acceptable, as BE-12 decided for scalars), and `bitcast` between vector types is `As<T>()`, free. Loads and stores use `LoadUnsafe`/`StoreUnsafe` (unaligned on every host; BE-15), honor `volatile`, and keep the 8-byte and 12-byte forms exact. Generic intrinsics map to `Abs`, `Sqrt`, `FusedMultiplyAdd` (`llvm.fma`; `llvm.fmuladd` may round twice, as today), `Min`/`Max` (`llvm.minnum`/`maxnum` and `minimum`/`maximum` have different NaN rules; the helper picks `MinNumber` or `Min` accordingly), `AddSaturate`/`SubtractSaturate`, `Floor`/`Ceiling`/`Truncate`/`Round`, the integer min and max, `ShiftLeft`/`ShiftRightArithmetic`/`ShiftRightLogical` by a scalar or a vector, `ctpop`/`ctlz`/`cttz` and `bswap` as compositions, and the reductions to `Sum`, `Max`, `Min` or a shuffle tree (the backend lowers `llvm.vector.reduce.*` itself, instead of `expand-reductions`, where .NET has the operation). Two idioms LLVM's x86 backend matches are recognized at the IR level, because the neutral API runs them 1.4 to 1.6 times slower than the instruction: the widen-subtract-abs-add of a byte sum of absolute differences and the widen-multiply-add of a 16-bit dot product become `Sse2.SumAbsoluteDifferences`/`MultiplyAddAdjacent` (and AVX2's) behind `IsSupported`, with the literal dataflow as the fallback (SV-21). Masked loads and stores stay scalarized (`scalarize-masked-mem-intrin`), because a masked access must not touch the masked-out bytes; `llvm.get.active.lane.mask` and the `vp.*` family stay rejected and `-fvectorize` keeps tail folding off.

Function boundaries. A vector parameter is a typed `Vector128<T>` (or fragments), which .NET passes in vector registers on ARM64 and on the stack on x64. A vector result of at most 16 bytes returns as the explicit-layout bytes it was before SV-02, which .NET returns in registers, because x64 returns a `Vector128` through a hidden buffer and NativeAOT then makes no fast tail call through a function pointer with such a result ([evidence](../evidence/2026-11-03-vector-lowering.md#a-vector-result-and-nativeaot-tail-calls)); the explicit-layout containers remain for aggregates that contain vectors. The `musttail` rule for 16-byte values is unchanged (BE-44). Variadic vector arguments take the SysV floating-point slots the software `va_list` already has.

Scalar fallback per function. Before translation, LLVM's scalarizer turns into scalar code each function whose vector code the lowering does not translate (lanes of no CIL vector type, vector `getelementptr`, vector intrinsics without a lowering), which keeps every program translatable as before, and each function whose vector code moves more lanes than it computes on: an inserted or extracted lane costs an instruction as a `Vector128` and none as scalars, and an operation on N lanes saves N - 1 scalar ones. That is the x86-64 ABI's two-float `<2 x float>` and SROA's small arrays, which made Bullet 4 to 5% slower typed (SV-02). `llvmnet -v` names each such function; the hidden `--vector-lowering=typed` keeps all translatable code typed, `scalar` scalarizes everything as before.

Widths. 128 is the default and runs everywhere. `--vector-width=256` keeps 256-bit IR vectors as `Vector256<T>`: on a JIT host with AVX2 and a NativeAOT build with `--aot-instruction-set x86-64-v3` they are single instructions; elsewhere .NET computes them as two 128-bit halves (measured at about 1.3 times a `Vector128` operation on this host with AVX disabled). The option is meant for `--isa=x86-64-v3` builds whose libraries use 256-bit intrinsics; the vectorizers are kept at 128 bits unless that level is requested. 512 bits are not planned: no supported host guarantees them and ILC does not enable AVX-512 opportunistically.

Autovectorization. The loop and SLP vectorizers are the first consumer of Level 1 and need no new compiler support once it exists: the portable target's cost model is x86-64 with SSE2, which emits exactly the 128-bit types above, and `--isa=x86-64-v3` adds the AVX2 model. What has to be measured, not assumed, is the gain on real code: the vectorizers' choices (interleaving by 2 to 4, 64-bit SLP vectors, the shuffle-heavy epilogues) cost more in CIL than in native code, because RyuJIT does not fuse what LLVM's backends fuse. The kernel measurement in the evidence bounds the gain (3.7 to 5x at 128 bits, about double at 256, on loops whose native vectorization gains 3 to 12x) and shows that LLVM's x86 cost model also emits `<4 x i8>` and `<4 x i16>` vectors, whose padded-lane lowering may not beat scalar code. SV-05 measures the benchmark set, tunes the knobs the driver passes (`-mllvm -slp-min-reg-size`, interleave counts, `-mprefer-vector-width`) and proposes the default. Until it reports, ADR-11's `-O1` scalar default stands: with the vector IR scalarized, `-O3 -fvectorize` costs 1.2 to 2x today.

SIMD128. With Level 1 the `wasm_simd128.h` header becomes mostly plain vector-extension code, as Clang's own header is, and keeps `__llvmnet_simd128_*` only for the operations that are `llvm.wasm.*` intrinsics in the real header (swizzle, bitselect, any/all true, bitmask, saturating narrows, `q15mulr`, dot, pairwise extended add, `pmin`/`pmax`, saturating truncations), which Level 2 serves through the same helper mechanism. `--simd128` remains as an alias of `--isa=wasm-simd128`; the HEVC profile's hashes and the oracle tests are the acceptance test (SV-07).

### Level 2: target intrinsics

Scope, by LLVM 22's intrinsic tables: SSE 37, SSE2 60, SSE3 9, SSSE3 27, SSE4.1 16, SSE4.2 18, AVX 56, AVX2 101, FMA 4 (328 in all; the half of the C intrinsics that Clang lowers generically needs nothing here); WebAssembly SIMD 25; NEON 209. Not in scope: AVX-512 and AVX10 (968 definitions, no supported host guarantees them), MMX (64-bit state semantics), XOP, SVE, the x87 control intrinsics (`_mm_setcsr` and `_MM_SET_ROUNDING_MODE` fail to compile, `_mm_getcsr` reads fixed values and prefetch is a no-op, as emscripten does).

Helpers. One static method per intrinsic in `LlvmNet.Runtime` (`Simd/X86.cs`, `Simd/Wasm.cs`, `Simd/Neon.cs`), typed as the intrinsic is, `AggressiveInlining`, with this shape:

```csharp
[MethodImpl(MethodImplOptions.AggressiveInlining)]
public static Vector128<byte> PShufB(Vector128<byte> value, Vector128<byte> indices) =>
    Ssse3.IsSupported ? Ssse3.Shuffle(value, indices)
    : AdvSimd.Arm64.IsSupported ? AdvSimd.Arm64.VectorTableLookup(value, indices & Vector128.Create((byte)0x8f))
    : Vector128.ShuffleNative(value, indices & Vector128.Create((byte)0x0f)) & Vector128.GreaterThan(indices.AsSByte(), Vector128<sbyte>.AllBitsSet).AsByte();
```

`IsSupported` is a constant for the JIT and for ILC's guaranteed sets, and a runtime check for ILC's opportunistic sets, so the same assembly gets `pshufb` on every x64 host (including NativeAOT at the default level, where the generic `Vector128.Shuffle` does not), `tbl` on ARM64, and the composition elsewhere. Exactness is the rule, not speed: `minps` returns the second operand when either is NaN, `cvtps2dq` returns `0x80000000` for out-of-range input, `psadbw` sums into 64-bit lanes, `pmulhrsw` rounds as the instruction does; every helper is tested against the native instruction on x64 (random inputs, the special values) and against its own composition with `DOTNET_EnableHWIntrinsic=0` and on ARM64. The backend recognizes the `llvm.x86.*` name and emits the call; the x86 warning and link error of SA-12 remain for intrinsics the table lacks, and `--report-simd` (SV-10) lists, per program, the helpers used by class (instruction-backed on x64, instruction-backed on ARM64, composed, scalarized), as emscripten's `WASM_SIMD_COMPAT_SLOW` does.

The frontend side: `--isa=<level>`. In portable mode the driver rejects `-m<...>` because it would change the ABI ([modes.md](../user/modes.md#portable-net-abi)); the SIMD feature flags do not, but a library keys its code paths on the macros they define (`__SSE2__`, `__SSSE3__`, `__AVX2__`), so the choice must be explicit. `--isa=x86-64-v2` passes `-march=x86-64-v2` to Clang for the portable target and stops undefining `__x86_64__`, `__SSE__` and `__SSE2__` (the libc++ and musl headers that size their helpers from them are unaffected: the sysroot is built at `baseline` and the layouts do not depend on the macros, which the ABI freeze test keeps checking); `x86-64-v3` adds AVX2 and FMA with `--vector-width=256`; `wasm-simd128` is today's header path; `neon` is SV-11. The level is recorded in the object (`llvmnet.isa` module flag) and in the image; objects of different levels link together, because the level changes only which instructions a function may use. In system mode `-m` options already work; `--isa` maps to `-march` there, and with the SSE2 to SSE4.2 helpers in place the predefined `__SSE2__` becomes harmless for the common libraries, which closes SA-12's option (c); whether to keep predefining the macros (its option (b)) is independent and stays the owner's.

NEON and WebAssembly sources. Clang's `<arm_neon.h>` needs an AArch64 target, which the portable target is not, so NEON source compatibility comes from a SIMDe-derived header set in the sysroot (`SIMDE_NO_NATIVE`: the intrinsics become vector-extension code for Level 1, plus `llvm.aarch64.neon.*` helpers for what SIMDe expresses badly, such as table lookups and pairwise operations); it is P2, because every library in the survey that has NEON also has an x86 or C path. WebAssembly's header is llvmnet's own, as today. A NEON-targeted library on an ARM64 host still runs the x86 or C path it was compiled for: the ISA level is a compile-time choice (one ISA per compile), and the host decides only how that level's operations execute.

### Level 3: native kernel packages

The problem Level 3 solves is assembly: ffmpeg's 185 nasm files, dav1d's 47 nasm and 43 `.S` files, libjpeg-turbo's 91 nasm files, OpenSSL's generated assembly, BLAS kernels. No translation of assembly to CIL is planned (lifting machine code to IR is a research project and would still not meet the libraries' own `checkasm` expectations). Instead the project's build assembles its kernels natively for each runtime identifier it wants to ship, and llvmnet calls them:

```
project build (Meson, CMake, configure): nasm -f elf64 / -f win64 / -f macho64; clang --target=aarch64-linux-gnu -c kernel.S
   -> runtimes/linux-x64/native/libfoo-kernels.so + .a, runtimes/linux-arm64/..., runtimes/win-x64/..., runtimes/osx-arm64/...
   -> kernels/manifest.json: name, version, symbols with their flags (leaf, callbacks), libraries per identifier
llvmnet --native-kernels=kernels/ program.bc -o program.dll
   -> for every undefined function the manifest lists: a DllImport stub with the declaration's CIL signature
      (scalars and pointers only; a struct by value, vector or long double parameter is a compile error naming the function),
      SuppressGCTransition when the manifest marks the symbol leaf (the default for assembly), bound lazily
   -> the image's initializer registers a DllImportResolver that loads runtimes/<rid>/native/ from the image directory
   -> NativeAOT: <NativeLibrary Include="runtimes/<rid>/native/libfoo-kernels.a"> and <DirectPInvoke Include="foo-kernels">
      conditioned on the RuntimeIdentifier, so the executable carries exactly one identifier's kernels, statically
   -> system mode: the same stubs; the objects are linked into the sidecar .so (JIT) or the static link (NativeAOT)
```

What crosses the boundary follows the extension rules of [11-native-extensions.md](11-native-extensions.md#what-crosses-the-boundary): exact C scalar types on the native side, pointers into the program's memory, `long` and `long double` rejected (`long` is 32 bits on Windows x64), structures by value rejected until NX-07, no callbacks in the first version (a kernel is a leaf function; a kernel that calls C needs a reverse thunk and is rejected unless the manifest declares the callback). The data the kernels read is laid out by the bitcode's `dotnet64-v2` rules, which are the LP64 layouts of every supported host for fixed-width types, pointers, `float` and `double`; a kernel that depends on anything else is the project's bug on that host, as it is natively.

Fallback and detection. A program built with a package still contains its C paths: the libraries dispatch at run time on CPU flags, and that dispatch is what selects a kernel. On a host for which the package has no library, the stubs are never reached if detection reports no features; a stub that is reached anyway fails fast with one `llvmnet:` line naming the symbol, the package and the identifiers it has. Detection therefore has to work without assembly (SV-12): `<llvmnet/cpu.h>` declares `uint64_t llvmnet_cpu_features(void)` (bits for SSE2 to AVX2, FMA, BMI, POPCNT, AVX-512 presence, NEON, DotProd, CRC, SVE presence, read from the `IsSupported` properties) and `int llvmnet_native_kernels(const char *package)` (whether the running host has a library for it); the runtime provides compiler-rt's `__cpu_model`, `__cpu_features2` and `__cpu_indicator_init` so `__builtin_cpu_supports` and `__builtin_cpu_init` link and answer in both modes; `target_clones` and `ifunc` lower to an initializer-time resolver call and an indirect call; the CPUID and XGETBV inline-assembly forms that system mode already recognizes are emulated in portable mode through `X86Base.CpuId` (zeros on a host without x86) and an XCR0 value synthesized from `Avx.IsSupported` and `Avx512F.IsSupported`, which is what ffmpeg's `ff_get_cpu_flags_x86` and dav1d's detection need; on ARM64 hosts musl's `getauxval(AT_HWCAP)` returns the NEON, CRC, DotProd and SVE bits derived the same way. With that, ffmpeg's and dav1d's unmodified x86 detection reports the host's x86 features on x64 and nothing elsewhere, so a single-ISA build selects its kernels exactly where they can run.

Multi-ISA bundles (SV-16) are the opt-in beyond the baseline: one image carrying `linux-x64` and `linux-arm64` kernels with a dispatcher that consults `llvmnet_cpu_features` for both families. The mechanism supports it (the package may hold any set of identifiers, and detection answers for the running host), but the library's dispatch code must be compiled for both (ffmpeg selects `ff_hevcdsp_init_x86` or `_aarch64` at configure time), so it is a per-project change, documented with ffmpeg as the worked example.

Building packages. nasm cross-assembles for ELF, COFF and Mach-O from any host, and Clang 22 cross-assembles `.S` for any registered target; linking the shared libraries of other operating systems needs lld (`ld.lld`, `lld-link`, `ld64.lld`), which is optional (a package may ship only the identifiers its build could link). `scripts/kernels.py` links the libraries and writes the manifest for a list of identifiers; SV-14 adds the assembling for Meson and CMake projects to call.

Shared data and optional kernels (found with ffmpeg, SV-13). Assembly reads tables that the C defines, and C reads tables that assembly defines, but a portable program's globals live in managed memory that the kernels cannot name. The manifest lists the shared variables; the package's libraries hold their storage and an accessor per variable, and where the host has the library the image takes the address from the accessor and copies the C initializer there, so both use one copy; elsewhere it allocates them as usual. A void kernel marked optional, such as ffmpeg's `ff_emms_asm`, which the C calls whatever the CPU, does nothing where the host has no library.

Inline assembly. The policy of BE-24 stands: rejection with the allowlist, extended by the CPUID and XGETBV emulation above. The ecosystem's SIMD inline assembly (ffmpeg's `HAVE_INLINE_ASM` paths, libwebp's) is legacy next to nasm and intrinsics, and every project in the survey builds without it; the error message names the project's switch (`--disable-inline-asm`, `WITH_SIMD`) where known. Functions that contain other inline assembly are Level 4's input.

### Level 4: compiler-generated native kernels (experimental)

A leaf function (no calls, no non-constant globals, no TLS, no `long double`, no varargs) that uses intrinsics outside Level 2 or inline assembly can be compiled by LLVM's own backends: in system mode into the sidecar `.so` and the NativeAOT static link, with the x86-64 backend (SV-17); in portable mode into a per-identifier kernel package that llvmnet itself generates (`--native-kernels=generate:linux-x64,linux-arm64,...`), keeping the CIL translation of the same function as the fallback for hosts without a package (SV-18). The portable form needs a data-layout compatibility check per function (the bitcode carries x86-64's layout; AArch64's differs in `x86_fp80` and preferred alignments only, which the constraints exclude), and it reintroduces native code into portable images, which is why it is experimental and a separate owner decision after SV-17 measures it on Skia's `skvx` kernels and the survey's astc-encoder.

### Testing

- Correctness first: the vector forms of the IR semantics probes (SV-04) compared with native bit for bit, as the 44,762 scalar probes are; `tests/vector-sweep.sh` promoted from "correct" to "vector code emitted" with an `inspect` count; every Level 2 helper against the native instruction on x64 and against its composition elsewhere; the SIMD128 oracle unchanged; kernel packages checked with dav1d's and ffmpeg's `checkasm` (they compare assembly with C, the oracle the projects maintain).
- Performance as a gate, not a hope: the benchmark set of ADR-08 plus the survey's reproducers (Skia nanobench subset, libjxl, dav1d, libjpeg-turbo, Opus) at each level, in the nightly table, with the native scalar and native vectorized builds as the two references.
- Every host: the `xp` bundle runs the vector fixtures on Windows x64, macOS ARM64 and Linux ARM64 under the JIT and NativeAOT; `DOTNET_EnableHWIntrinsic=0` runs exercise every composition on the build host.

### Options summary

| Option | Modes | Meaning |
| --- | --- | --- |
| `--isa=<level>` | both | `baseline` (default), `x86-64-v2`, `x86-64-v3`, `wasm-simd128` (`--simd128`), `neon` (SV-11): intrinsics, macros and vectorizer features; no data ABI change; recorded in the object |
| `--vector-width=<bits>` | both | 128 (default) or 256: whether 256-bit IR vectors stay `Vector256<T>`; implied by `--isa=x86-64-v3` |
| `--native-kernels=<dir>` | both | a kernel package to resolve undefined functions against; `generate:<rids>` is SV-18 |
| `--report-simd` | both | per-program report of vector operations and helpers by class |
| `-fvectorize`, `-fslp-vectorize` | both | as today; SV-05 proposes the default |
| `--aot-instruction-set` | NativeAOT | adds `x86-64-v2`, the default for a program with `x86-64-v2` objects (SV-08); `x86-64-v3` pairs with `--isa=x86-64-v3` |
