# Architecture

The pipeline below is shared by three explicit runtime selections: legacy `managed-host`, native `system`, and versioned `portable`. [toolchain.md](toolchain.md) defines their ABI and deployment contracts; host-layout details below are not portable host-library interfaces.

## Pipeline

1. The driver invokes clang-22 for C/C++ or flang-22 for Fortran and emits LLVM bitcode. Frontend optimization defaults to O1 with automatic vectorization disabled; explicit frontend arguments can override defaults.
2. The small C++ bridge uses LLVM's parser, archive reader, linker, verifier, and exact numeric-constant APIs. It performs real lazy archive-member extraction. This bridge runs only inside the compiler process.
3. Executable links internalize definitions except the entry points and run global dead-code elimination. Library links preserve public definitions. Both expand vector reductions and run LLVM's scalarizer before CIL emission. The default also scalarizes vector loads/stores; `--simd128` retains them and recognized SIMD helper calls. ABI tags reject incompatible object/archive members.
4. The C# backend reads LLVM through its C API. LLVM data layout determines sizes, alignments, and structure offsets.
5. `PersistedAssemblyBuilder` emits static CIL methods and a managed PE image. The .NET JIT executes those methods normally.
6. Optional NativeAOT consumes the emitted CIL executable directly. System-mode ABI bridges become static native inputs, permitting a single executable to be staged by ordinary build/benchmark tools.

## Values and Control Flow

LLVM SSA values map to typed CIL locals. Basic blocks use CIL labels. PHI copies are evaluated before any destination is updated, preserving parallel assignment on every incoming edge. Switch case values use the LLVM 22 switch API, not operand-number assumptions.

Integers through 32 bits use CIL `int32`, through 64 bits use `int64`, and through 128 bits use `UInt128` plus explicit signed/unsigned helpers. Narrow values are normalized to their LLVM bit width. Signed operations extend from that width before operating. Odd-width memory stores touch only the bytes occupied by the LLVM value.

LLVM `float` and `double` use their CIL equivalents. `x86_fp80` uses a 16-byte-layout software value with a 64-bit significand, full extended exponent range, and round-to-nearest-even arithmetic. Its constants are extracted bit-for-bit through LLVM. There is no silent long-double-to-double substitution. Other extended floating types remain unsupported.

`llvm.fmuladd` uses separately rounded multiplication and addition, which LLVM permits and which matches the generic native test baseline. `llvm.fma` remains fused. Saturation, overflow, ordered/unordered comparisons, signed zeros, and bit-width behavior have focused IR tests.

Explicitly enabled frontend vectorization uses a scalar semantics fallback, not hardware SIMD. LLVM expands reductions and scalarizes arithmetic, casts, comparisons, shuffles, selects, and ordinary vector memory operations. Residual fixed-vector arguments/results use explicit-layout value storage with lane insertion/extraction, including bit-packed integer masks. Tests cover ordered floating reductions, wrapping integers, dynamic lane indices, packed constants, relocations, narrowing, and loop tails. Scalable vectors, target-specific intrinsics, and complete masked-memory support remain unsupported. No assumption is made about `Vector<T>.Count`.

LLVM 22's scalarizer can corrupt the terminator of a vector-returning `invoke`. Before scalarization, llvmnet wraps those returns in a one-field aggregate and inserts a normal-edge extraction block, preserving PHI predecessors and the original unwind edge. Native-oracle tests cover both normal and exceptional results under both ABIs and JIT/NativeAOT; the VPR workload exposed this case.

The opt-in [SIMD128 source-header path](simd128.md) maps exactly 128-bit vector storage to `Vector128<byte>` and leaves explicit managed SIMD helper calls plus vector loads/stores intact. The helpers use typed `Vector128<T>` reinterpretations for lane semantics and can be inlined by the JIT/AOT compiler. The ordinary scalarizer still handles unrelated vector arithmetic. Native vector-valued callbacks remain rejected. The original WebAssembly oracle now checks the emitted compiler path as well as the standalone API prototype; ffmpeg's unchanged wasm HEVC IDCT/SAO C kernels exercise the implementation in both ABIs.

## Memory and Calls

Pointers are native integers into unmanaged memory or stack storage. Globals and constant aggregates are allocated before their initializers and relocations are installed. Defined TLS globals use lazy per-thread accessors with initialized storage; external native TLS globals still require a bitcode definition. Function-pointer tables use `ldftn`; known translated targets use managed `calli`, including system-mode callbacks. Native identities remain available for supported C callbacks. Managed aggregate call signatures are finalized after persisted type tokens exist, then recorded `calli` operands are patched through structured PE metadata.

Large initialized globals are embedded in at most 1 MiB data fields and copied into one contiguous allocation; relocations are applied afterward. Functions with more than 32,768 SSA results and no setjmp sites reuse primitive locals whose uses stay within one block. Cross-block scalar values, including PHIs and invoke results, use typed per-call arrays to avoid the CIL local-index limit. Cyclic PHI copies still load every source before storing destinations. Large aggregate-heavy or setjmp methods can still exceed the local limit and are not claimed as supported.

Arrays/structures are explicit-layout managed value types used as bit containers, not GC object graphs. Loads/stores use unaligned-safe CIL or exact-width helpers. Ordinary allocas use aligned stack allocation. Functions with stack-save/restore or nonlocal-jump sites use scoped aligned allocations, save allocation checkpoints, and release storage on restore or unwind. `byval` parameters receive a private aligned copy; hidden `sret` pointers are preserved. Direct `setjmp` sites resume through a managed exception dispatcher in the owning activation, preserving live locals and restoring allocation checkpoints. This does not support jumping across native frames.

Variadic calls construct a software x86-64 SysV register-save and overflow area. Translated `va_start`, `va_copy`, and `va_arg` sequences and managed libc formatting functions consume the same layout. Variadic aggregate ABI classification is incomplete; scalar integer/pointer/float overflow-register cases are tested.

System-mode internal variadic callbacks use distinct unmanaged-callable identities registered against their managed implementations. Translated indirect variadic calls resolve these identities before using managed `calli` with the software argument area. Registered native variadic functions instead use LLVM-generated indirect thunks with the actual call-site signature, including floating-point register overflow and long-double arguments. Unregistered native variadic pointers are rejected. Native invocation of translated variadic or aggregate callback identities terminates with an explicit diagnostic. Pointer identity, legacy fixed callbacks, mixed register/stack arguments, formatting, and these boundary errors are tested under JIT and NativeAOT.

Legacy C no-prototype call sites may use a variadic LLVM signature even when the linked definition is fixed-arity. Direct calls use that definition when the required argument types match, without appending a spurious variadic frame. Unused trailing arguments, including Fortran hidden character lengths, are not pushed for fixed definitions. A void call site discards a non-void definition's unused result; a non-void call to a void definition is accepted only when the result has no uses. Other incompatible signatures are diagnosed instead of emitting invalid CIL. NativeAOT xz, nab and gem5 workloads exercise these cases.

System-only direct calls also match verified x86-64 C ABI scalar-slot behavior: i32 register arguments zero-extend to i64, i64 arguments narrow to low i32 bits including stack slots, and pointer/i64 arguments preserve their bits. Byte/boolean parameter and return mismatches use tested low-bit conversions. Aggregate/register-class changes, incompatible argument attributes, non-C conventions and stack widening remain rejected. These rules support specific legacy interfaces, not portable C/C++ language-level compatibility. Missing required arguments remain compile errors by default; the system-only `--trap-missing-arguments` option emits a diagnosed exception at invalid void-call sites. It does not supply missing values or silently skip execution.

## Runtime

Managed exports are explicitly marked with `CExportAttribute` and checked against LLVM signatures. The runtime provides selected allocation, string, formatting/scanning, math, file, time, environment, pthread, atomic, signal, and filesystem interfaces. OS access goes through .NET APIs. P/Invoke is not used to execute native ffmpeg or substitute its algorithms.

Atomics deliberately use managed synchronization for correctness before performance. Portable and legacy pthreads map to managed threads, mutexes, condition waiters, once controls, and key destructors. System mode uses native pthreads and synchronization with managed-entry/TLS-destructor adapters. Both paths pass the threaded ffmpeg checks described in [ffmpeg-threading.md](ffmpeg-threading.md). This does not imply full pthread or POSIX support. Metadata such as `stat` and directory inode values is only partially modeled; ownership changes return an unsupported-operation error. Signal behavior cannot reproduce arbitrary native asynchronous stack interruption.

System OpenMP can explicitly link LLVM's native C runtime. Outlined benchmark functions remain translated CIL and execute through native-callable scalar thunks. A four-worker fixture covers scheduling, reductions, critical sections and barriers; portable OpenMP, offload and arbitrary OpenMP worker TLS teardown remain outside this tested boundary.

Floating atomic exchange/add/subtract uses the same synchronization as integer atomics, preserving the old value and float/double arithmetic. Host DO CONCURRENT lowering uses the same native OpenMP boundary. Separate native-oracle fixtures check four-worker updates and concurrent Fortran loops. Float80 floor operates on the exact signed significand and scale, without conversion through double.

C++ `invoke` becomes a CIL try/catch region, landing pads select matching C++ exception types and exception-specification filters, and resume/rethrow propagates managed exceptions carrying the C++ object. Public single/multiple/virtual-base RTTI supports tested adjusted catches and dynamic casts. The runtime tracks uncaught exceptions and runs known translated C++/TLS destructors through managed calls. System libstdc++ exception pointers retain reference-counted primary objects; dependent rethrows keep separate catch/unwind state, including concurrent rethrows. Primary initialization without throwing supports make_exception_ptr and releases failed-copy storage. Terminate handlers use atomic registration and managed target resolution; returning or throwing handlers abort rather than allowing C++ code to resume. Selected upstream libstdc++ source units and the GCC demangler can be linked as an explicit system-ABI bitcode archive for streams, locales, containers, threads, futures, OS entropy, regexes and filesystem operations. This is not a complete libstdc++ runtime or native C++ ABI, and does not supply portable libc++ facilities.

Fortran uses Flang 22 CFI descriptors: a 24-byte header followed by rank-dependent 24-byte dimension records and optional derived-type addenda. Implemented intrinsic arrays preserve extents, lower bounds, and byte strides. Pointer allocation preserves prior associations and tracks runtime-owned targets for deallocation through aliases. Contiguity inquiries and temporary copy-in/copy-out preserve noncontiguous array sections without reallocating the destination. Allocation, intrinsic assignment, reductions, PACK/RESHAPE/TRANSFER, dynamic array constructors, deferred-length characters, command arguments and byte-character searches are managed runtime operations. Date/time and clock queries use .NET; seeded random sequences reproduce Flang's Park-Miller generator for tested real kinds.

The Fortran I/O subset includes formatted/list-directed records, tested explicit E/ES/G exponent widths, intrinsic namelist input/output, logical input, file/unit inquiry, non-advancing writes and sequential/stream/direct unformatted transfers. Sequential unformatted files use checked four-byte record markers and optional component byte swapping. Direct unformatted records require positive RECL and one-based REC, seek to checked fixed-record offsets, and transfer without markers; sequential positioning statements reject direct units. Flang FORT_CONVERT defaults and environment overrides select byte order. RECL limits output records, and IOLENGTH sums transferred component bytes. Empty sequential reads consume records, ENDFILE truncates at the current position, and BACKSPACE distinguishes the endfile position. Scratch units are unnamed temporary storage deleted on close. Environment, SIZE, pointer-target association and real-model inquiries use the corresponding descriptor or numeric operations. Descriptor-stack operations copy complete descriptor metadata without acquiring ownership of its targets.

Derived metadata drives default initialization, recursive allocatable-component cleanup and component-wise I/O without structure padding. Intrinsic assignment supports matching metadata that proves no owned components, finalization or defined assignment are needed; pointer components retain association and overlapping source values are staged. Final procedures, defined I/O/assignment, general owned-component assignment, parameterized components, formatted direct access, segmented records, value stacks, coarrays and complete editing semantics remain unsupported. Non-advancing error timing and arbitrary concurrent Fortran I/O are not fully modeled.

## Linking Boundaries

- LLVM bitcode linking is static and uses `-L` / `-l` or explicit object/archive paths.
- Managed linking uses `--cil-reference` and `CExport` methods.
- Native linking uses explicit `--native-import symbol=library!entrypoint` mappings and emits P/Invoke metadata.

These boundaries must not be conflated. In particular, a native function cannot consume a managed `ldftn` callback as an ordinary C callback. The explicit P/Invoke path rejects unsupported native aggregate signatures. System mode instead generates LLVM ABI bridge calls and unmanaged-callable callback methods. Portable mode uses only its own managed callback and header ABI and rejects native import options.
