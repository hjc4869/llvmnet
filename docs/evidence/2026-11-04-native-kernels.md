## The mechanism

`--native-kernels <dir>` reads a package's `manifest.json` (name, version, library name, per runtime identifier a shared and a static library, the symbols with their leaf flag). Every function the program declares and the package lists gets, in the image, a wrapper with the declaration's managed signature and two P/Invoke methods of the native signature (`int` for integers up to 32 bits, `long`, `nint`, `float`, `double`). The wrapper extends narrow arguments as their `signext` or `zeroext` attribute says, calls the P/Invoke that `RuntimeFeature.IsDynamicCodeCompiled` selects (a constant to ILC, and to the JIT once `RuntimeFeature` is initialized, as its getter reads a static read-only field; `NativeKernels.Register` reads it in the image's initializer before any kernel is compiled) and keeps the low bits of a narrow result:

- Under the JIT, the P/Invoke's library name is `llvmnet-kernel:<package>:<symbol>`, and it binds at its first call. The image's initializer registers the package with `NativeKernels.Register`, whose `DllImportResolver` then loads `runtimes/<rid>/native/<library>` from beside the image (llvmnet copies every identifier's shared library there) or ends the process with a line naming the kernel, the package and the identifiers it has.
- As NativeAOT, the P/Invoke names the package's library, `SuppressGCTransition` for leaf kernels, and the generated project links each identifier's static library with `DirectPInvoke` for that library, both conditioned on `$(RuntimeIdentifier)`.

The JIT's P/Invoke keeps the GC transition because a P/Invoke without it has no lazy binding stub: RyuJIT binds it whenever it compiles a method that calls it. With `SuppressGCTransition` under the JIT, compiling `main`, which merely could call a kernel, ran the resolver and ended the process on a host without the library, and `RuntimeHelpers.PrepareMethod`, which `tests/jit-validation.sh` calls on every method, failed on an image whose library was not beside it. Unoptimized code (tier 0) also keeps the NativeAOT branch of the constant test, whose transition-free P/Invoke the JIT then bound; the wrapper is therefore `AggressiveOptimization` as well as `AggressiveInlining`. A function pointer to a kernel is the wrapper's, so DSP tables work as they do for C functions. `llvmnet_native_kernels(name)` (`<llvmnet/cpu.h>`) answers whether the running host has the package's library. A variadic kernel, or one with a `byval`, `sret` or similar parameter, is a compile error naming it; the image lists its packages in `llvmnet.kernels`.

## The synthetic package

[tests/kernels/synthetic](../../tests/kernels/synthetic) has five kernels in x86-64 System V, x86-64 Windows, AArch64 ELF and AArch64 Mach-O assembly: an SSE2 or NEON `int32` add, a sequential `double` dot product, `int16_t sk_mix(int8_t, uint16_t, int64_t, float)`, whose System V version relies on the caller's extension of its narrow arguments, `sk_weighted`, which reads a constant table and a variable that the program defines, and `sk_count`, which increments a table that the package defines and the program reads and writes. The program calls them through a table and directly, with C fallbacks it selects by `llvmnet_native_kernels`. [tests/native-kernels.sh](../../tests/native-kernels.sh) assembles the four object files with Clang and makes the package with [scripts/kernels.py](../../scripts/kernels.py), which links each identifier's shared library with lld; the xp bundle carries the package and the program as the `kernels` fixture.

| host and engine | library | result |
| --- | --- | --- |
| Linux x64, JIT | linux-x64 shared library, loaded at the first kernel call | as native linked with the kernels |
| Linux x64, NativeAOT | linux-x64 static library, no dynamic dependency | as native |
| Linux x64, JIT, library removed | none | the C paths, as native; with the argument "kernels" exit 127 and llvmnet's message |
| Linux ARM64 (qemu), JIT | linux-arm64 shared library | as native |
| Windows x64 (fluorite), JIT and NativeAOT | win-x64 DLL; static library linked by MSVC's linker | as native; without the DLL the C paths, and exit 127 with the message |
| macOS ARM64 (mainmac), JIT and NativeAOT | osx-arm64 dylib; static library linked by Xcode's linker | as native |

The xp bundle passes on Windows x64 and macOS ARM64 (75 passed each, 4 skipped for want of GLES and Vulkan libraries, as before) and runs the `kernels` fixture as native on Linux x64 (JIT and NativeAOT) and Linux ARM64 (JIT). A first Windows NativeAOT build loaded `synthetic-kernels.dll` at startup: lld-link had written its import library over the static library beside the DLL, so the helper passes `/noimplib`, and the test checks that the static libraries hold the kernels.

## Shared data

Assembly reads tables that C defines (ffmpeg's `ff_pw_*` constants and its transform tables, which C fills at run time), and C reads tables that assembly defines. Both must use one copy, and in portable mode the program's globals live in managed memory the kernels cannot name. The manifest's `data` names the shared variables; each package library defines their storage and an accessor, `llvmnet_kernel_data_<name>`. Where the host has the library, the image's initializer takes the address from the accessor instead of allocating, then copies the C initializer there; otherwise it allocates as usual. A variable that only the kernels define gets zeroed storage of its declared size on such hosts, not null: the first version stored null, and at `-O1` LLVM loaded from both arms of `kernels ? sk_counts : c_counts` before the select, as a declared global may be dereferenced, so the C path crashed. The accessors are not inlined: `tests/jit-validation.sh` loads images into a collectible context, where the JIT compiled the initializer with full optimization before `RuntimeFeature` was initialized, so the inlined accessors' NativeAOT branch stayed and its import was bound, which failed. `llvmnet --print-kernel-data=<names>` (hidden) links the program's bitcode and writes the storage, with each variable's size and alignment, and the accessors as C for the package's build.

## The package helper

`scripts/kernels.py` takes, per identifier, the native objects or the project's archives (it extracts their ELF, COFF and Mach-O members) and the program's bitcode. It reads the objects' symbol tables for the functions they define and the data they define or reference, rejects references to functions of the program, generates the data source with `--print-kernel-data`, compiles it with Clang for the identifier, and writes a static library (`llvm-ar` in GNU, COFF or Darwin format) and a shared one: `ld.lld -shared -Bsymbolic --no-undefined` after giving the objects' symbols default visibility (ffmpeg's x86inc marks every symbol hidden), `lld-link /dll /noentry /nodefaultlib /noimplib` with each function and datum exported, or `ld64.lld -dylib`. `--exclude` leaves a function to the program, `--not-leaf` and `--optional` set the manifest flags. The archives llvmnet links keep their native members: with `--native-kernels`, the linker leaves them to the package; without, it names the first one as a native object. lld-22 moves to the base package set (`scripts/ci/install-packages.sh`), nasm to the integration set.

Optional kernels are the other addition: ffmpeg calls `ff_emms_asm` after its MMX kernels whatever the CPU, as `emms_c()`, and some of its kernels then use x87 instructions (`float_dsp.asm`, `lls.asm`, `sbrdsp.asm`), so the call must stay a real `emms` where the kernels run. Marked `"optional": true`, a void kernel's wrapper returns at once where the host has no library.

## ffmpeg with its nasm kernels

`FFMPEG_X86ASM=1 LLVMNET_RUNTIME=portable scripts/build-ffmpeg.sh` configures the browser profile with `--enable-x86asm --x86asmexe=nasm` and run-time CPU detection, which assembles 91 of ffmpeg's 186 nasm files for the profile's components (68 in libavcodec, 9 in libavutil, 11 in libswscale, 3 in libswresample) into the libraries' archives beside 605 bitcode objects, then makes the `ffmpeg-x86` package from those archives (2,989 functions, 126 shared variables: 53 C tables the assembly reads and 73 the assembly defines; a 2.1 MB shared and a 2.4 MB static library; 1.5 s) and links the decode harness with it. The profile needs three things beyond the package: `libavutil/x86/cpuid.asm` in C ([config/ffmpeg-x86-cpuid.c](../../config/ffmpeg-x86-cpuid.c)), so that CPU detection runs on every host and answers through SV-12's CPUID; `HAVE_EBX_AVAILABLE 0`, because `libavcodec/msmpeg4.c` guards its inline assembly by that alone and configure's probe passes with llvmnet's `-c`; and `ff_emms_asm` optional.

Every engine's MD5 of each of 240 frames equals native's (the system-mode build's native decoder) for the 1080p clips of the benchmark set (HEVC 10-bit, H.264), with four frame threads: the package build under the JIT and as NativeAOT, and the same profile built natively with Clang and nasm. [tests/ffmpeg-x86asm.sh](../../tests/ffmpeg-x86asm.sh) decodes HEVC 8-bit, HEVC 10-bit and H.264 fixtures through the kernels under the JIT, with AVX off (ffmpeg then selects its SSE kernels) and as NativeAOT, and compares each with the same image's C paths, which it takes with hardware intrinsics off (CPUID reports nothing); without the library the C paths decode, and a kernel called with AVX2 reported ends the process naming `ff_hevc_add_residual_4_8_mmxext`. In the arm64 container under qemu the image decodes HEVC and H.264 through its C paths, with the same hashes.

Decoding the 240 frames, median seconds of five runs in alternating order (`scripts/ab-time.py`; each run a new process, so the JIT columns include about 0.5 s of startup and compilation). `native asm` is the profile built natively with Clang 22 at `-O1` without vectorization and with nasm (without libdav1d, which this host does not have and these clips do not use); `native scalar` the system-mode build's native decoder; `scalar` the portable build without assembly:

| HEVC 1080p 10-bit, 1 | 1.136 | 2.109 | 2.000 | 1.558 | 2.978 | 2.446 |
| HEVC 1080p 10-bit, 4 | 0.470 | 0.777 | 1.080 | 0.615 | 1.396 | 0.898 |
| H.264 1080p, 1 | 0.673 | 1.322 | 1.604 | 0.910 | 2.550 | 1.736 |

As NativeAOT the kernels make the decode 1.57 (HEVC) and 1.91 (H.264) times faster than the scalar portable build on one thread, and it takes 1.37 and 1.35 times as long as the native assembly build, against 2.15 and 2.58 without them; with four threads it is within 1.31 and 1.41 times native. The remaining gap is the translated C (CABAC, the parsers), which runs slower than native C as the scalar columns show, and the kernel calls' transitions.

## What remains

System mode calls native libraries through `--system-library`; its kernel objects and archives are SV-15's. Packages for `linux-x64`, `linux-arm64`, `win-x64` and `osx-arm64` link here; ffmpeg's package is linux-x64 only, as its Windows and macOS objects need nasm's `win64` and `macho64` builds of the same profile and its AArch64 kernels a configuration whose dispatch code is compiled for both families (SV-16).
