# Evidence: closing the M3 to M5 exit items (2026-10-31)

Host: Linux x86-64 (Debian 13), 32 logical CPUs, .NET SDK 10.0.403, LLVM/Clang/Flang 22.1.8. Every number below was produced by a command in this repository; licensed SPEC material is not included.

## LC-09: time zones without zoneinfo

Where the host has no zoneinfo file, the host layer serves a TZif image generated from .NET's `TimeZoneInfo` (`src/LlvmNet.Runtime/Host/HostZoneInfo.cs`, contract in [dev/host-abi.md](../dev/host-abi.md)). `tests/zoneinfo.sh` builds `tests/c/zoneinfo.c` natively and in portable mode and converts instants between 1902 and 2037 (every 37 days and 5 hours, and every hour of 2024 for three zones) in 13 zones: Europe/Berlin, America/New_York, Australia/Lord_Howe, America/St_Johns, Asia/Kolkata, America/Sao_Paulo, Pacific/Auckland, Asia/Tehran, Pacific/Apia, Asia/Kathmandu, Europe/Moscow, Africa/Casablanca, UTC, plus the local zone.

| Comparison | Conversions | Result |
| --- | ---: | --- |
| Portable with the host's zoneinfo files against native glibc | 45,056 | identical |
| Portable with generated images (`LLVMNET_ZONEINFO=managed`) against native, JIT and NativeAOT | 43,688 | identical |
| The 1,368 conversions left out: instants whose tzdata offset has seconds (local mean time, America/St_Johns until 1935, Asia/Tehran until 1946) | 1,368 | `TimeZoneInfo` rounds these offsets to the minute; every difference is below one minute |

The unit tests (`tests/LlvmNet.UnitTests/HostZoneInfoTests.cs`, 14 tests) check that every instant in a generated image resolves to the offset and daylight flag `TimeZoneInfo` reports, and that the POSIX footer states tzdata's current rule (`<-05>5<-04>4,M3.2.0,M11.1.0` for America/New_York). A zone .NET does not know is `ENOENT`, after which musl falls back to UTC as it does for a missing file.

## CX-06: libc++ localization

`tests/libcxx-conformance.sh std/localization` after the lit configuration stopped advertising the named locales (musl accepts every locale name and behaves as C.UTF-8 under all of them, so libc++'s probes believed `fr_FR.UTF-8`, `ru_RU.UTF-8` and the others existed):

| Run | Passed | Failed | Unsupported | Pass rate |
| --- | ---: | ---: | ---: | ---: |
| Before (`cb0e334`, evidence of 2026-10-30) | 283 | 47 | 3 | 85.8% |
| After | 261 | 0 | 72 | 100% |

The 69 newly unsupported tests all `REQUIRES` a named locale (`locale.en_US.UTF-8` and the others): the 47 former failures and 22 tests that passed because they only used what C.UTF-8 provides. The sysroot has data for C and C.UTF-8 only (LC-20); on a platform with those locales installed the same tests would run.

`tests/libcxx-conformance.sh std/input.output`, rerun the same day: 574 passed, 13 failed, 2 death tests, 55 unsupported, 97.8%. The 13: 12 need what .NET cannot provide (LC-30): 8 tests whose fixtures create FIFOs or Unix sockets (`file_size`, `file_type_obs`, `hard_link_count` of `directory_entry`, `copy`, `copy_file`, `equivalent`, `hard_link_count`, `is_empty`), `create_hard_link`, `status` and `symlink_status` (which `bind` a Unix socket) and `remove_all/toctou` (race-safe `openat`); the last, `path.io.unicode_bug`, is marked `XFAIL: *` upstream and passes here, which lit reports as a failure. input.output therefore stays 0.2 points under the 98% bar of the M4 exit, for services the host layer does not have.

### OpenMP SPEC speed entries in portable mode

`scripts/spec-portable-check.sh` on the 25 speed entries that need OpenMP, with the toolchain packaged after FT-08, four threads, test inputs, `-O3`, NativeAOT:

| Result | Entries |
| --- | --- |
| PASS (22) | 603.bwaves_s, 619.lbm_s, 627.cam4_s (after the stack fix below), 628.pop2_s, 638.imagick_s, 644.nab_s, 649.fotonik3d_s, 654.roms_s, 657.xz_s, 800.pot3d_s, 803.sph_exa_s, 807.ntest_s, 809.cactus_s, 811.tealeaf_s, 816.nab_s, 820.cloverleaf_s, 849.fotonik3d_s, 854.graph500_s, 857.namd_s, 865.roms_s, 867.nest_s (with its `-include sys/time.h` setting), 881.neutron_s |
| FAIL, glibc behavior (1) | 607.cactuBSSN_s: overlapping `sprintf`, as 507.cactuBSSN_r |
| FAIL, prototype contradicts the definition (2) | 822.palm_s: four-argument `open`, as 722.palm_r; 621.wrf_s: `omp_get_thread_num` implicitly `REAL` (`float ()` against `i32 ()`), which the native runtime hides |

With nest, femflow and the 22 OpenMP entries, 91 of the 101 CPU 2017 and CPU 2026 entries pass in portable mode, against 67 after LC-31. The other 10: `fork` (500.perlbench_r, 600.perlbench_s, 827.cppcheck_s), glibc behavior (507.cactuBSSN_r, 607.cactuBSSN_s, 737.gmsh_r, 748.flightdm_r) and prototypes that contradict the definition (722.palm_r, 822.palm_s, 621.wrf_s).

627.cam4_s overflowed its stacks twice over. Its dynamics routine needs more than 8 MB on the main thread, which SPEC's own guidance covers with an unlimited stack limit (the harness sets it, and .NET's main thread honors it: a probe allocates 600 MB on the stack under JIT and NativeAOT). Its physics, on the OpenMP workers, needs tens of megabytes: the COSP simulator alone holds 75 MB of automatic arrays, which llvmnet keeps on the heap because the routine saves and restores the stack, but the frames above it still exceed the 8 MB every managed thread got, because the host ignored the stack size `pthread_create` asked for. Native libomp sizes its workers by `RLIMIT_STACK`, so the fix is two host changes: `getrlimit(RLIMIT_STACK)` now reports the process's real limit on Linux (from `/proc/self/limits`), and a thread's managed stack is at least the size of the mapping musl allocated for it, so `pthread_attr_setstacksize` and `OMP_STACKSIZE` take effect (`tests/thread-stack.sh`, and `tests/portable-openmp.sh` checks a 12 MB worker frame under a 16 MB limit and an 80 MB one under `OMP_STACKSIZE=96M`). With 256 MB worker stacks and an unlimited main stack, the JIT build of cam4 ran the test workload to completion, and with the fix 627.cam4_s passes the SPEC check in portable mode.

Two runs were needed for 809.cactus_s and 803.sph_exa_s: their parallel regions pass 49 and 17 variables, more than the 15 arguments libomp's generic C invoker handles, so the linker now gives such a region a thunk that takes the runtime's argument array (`tests/c/openmp-many.c` covers 21 variables); both pass with it. Worker stacks default to 4 MB as on x86-64 (`ports/openmp/llvmnet.patch`).
