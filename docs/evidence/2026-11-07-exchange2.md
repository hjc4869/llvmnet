**`digits_2`** is the brute-force search, a recursive subroutine with nine nested `DO` loops over a row's candidates (2,130 LLVM instructions, 222 IL locals). Most iterations reject a candidate at once (`if (block(row, k, i) <= 0) cycle`). Native code runs that path in registers, its row pointer stepped by LLVM's loop strength reduction:

```
inc  r13 ; add r12,0x144 ; add r15,0x144 ; dec ebx ; dec ebp ; jle ...
imul rax,r13,0x144 ; cmp DWORD PTR [rax+rdi*1-0x70],0x0 ; jle (back)
```

llvmnet's code loads the loop's trip counter and index from stack slots, decrements and increments them into two other slots, compares the old counter in memory, and on the next iteration copies both back into the slots of the loop's phis before computing the row offset again:

```
mov ebx,[rbp-0x288] ; dec ebx ; mov [rbp-0x2b8],ebx ; mov rbx,[rbp-0x2a8] ; inc rbx ; mov [rbp-0x2b0],rbx
cmp DWORD PTR [rbp-0x288],0x1 ; jg
mov ebx,[rbp-0x2b8] ; mov [rbp-0x288],ebx ; mov rbx,[rbp-0x2b0] ; mov [rbp-0x2a8],rbx
dec rbx ; imul rbx,rbx,0x144 ; mov [rbp-0x3a0],rbx ; cmp DWORD PTR [rdx+rbx*1+0x68],0x0 ; jle
```

Samples after an instruction that reads or writes a stack slot are 32% of llvmnet's `digits_2` (53 s), 19% of native's (21 s).

**`new_solver`** is the logic solver with its six contained procedures inlined, natively too (142 KB of machine code, llvmnet's 226 KB): 27,829 LLVM instructions, 7,878 blocks and 1,726 IL locals, more than the 1,024 RyuJIT tracks (`JitMaxLocalsToTrack`); untracked locals always live on the stack. Its samples are spread thin (no instruction above 0.9%), and 9.9 of its 17.8 s follow a stack-slot access against 0.6 s natively. Publishing the same project with `--codegenopt:JitMaxLocalsToTrack=1000` (ILC parses the value as hexadecimal without a prefix, 4,096; `0x1000` is ignored) makes the function 188 KB instead of 226 KB but only 3% faster (16.11 s against 16.54 s, side by side), so its stack traffic is RyuJIT's register allocation in a method of that size, not the tracking limit.

## PF-29: the cause in `digits_2`

flang's `DO` loop keeps an index and a trip counter, both phis of the loop header:

```llvm
%indvars.iv2762 = phi i64 [ %67, %.lr.ph2675 ], [ %indvars.iv.next2763, %.loopexit2532 ]
%.021932673 = phi i32 [ %60, %.lr.ph2675 ], [ %1183, %.loopexit2532 ]
...
%1183 = add nsw i32 %.021932673, -1
%indvars.iv.next2763 = add nsw i64 %indvars.iv2762, 1
%1184 = icmp sgt i32 %.021932673, 1
```

PF-22 joins a phi with a value it copies when no live segment of one meets one of the other, and it placed an instruction's operand reads and its result write at one position: `%indvars.iv.next2763`'s segment started where `%indvars.iv2762`'s last use ended, they met, and the index's next value took a local of its own, copied into the phi's on every back edge. That is the case PF-22's evidence left open ("101 that interfere with their phi, mostly an induction variable's next value", in `S_regmatch`). Natively the register coalescer ties them, because x86's `add` is a two-address instruction.

The counter has a second reason: InstCombine writes the exit test on the old counter (`icmp sgt %cnt, 1` for `%cnt - 1 > 0`), which keeps it live past the decrement; LLVM's loop strength reduction moves the test back to the decremented value in the native backend. Rewriting those 13 tests in the bitcode by hand (`artifacts/exchange2-prof/exchange2-postinc.ll`) changed nothing measurable on top of PF-29 (153.8 against 153.9 s and 154.7 against 154.2 s, two swapped rounds), so the compiler does not do it. Joining back-edge values before loop-entry values, also tried, left `digits_2`'s machine code identical.

## The change

`FunctionEmitter.ShareFunctionLocals` measures the live segments it compares in doubled positions: an instruction reads its operands at 2p and writes its result at 2p + 1 when the result is a scalar (integer of at most 64 bits, pointer, `float` or `double`) of an arithmetic, bitwise, shift, cast, comparison, `getelementptr` or `select` instruction (`ReadsBeforeWriting`). Those `Emit` pushes from their operands and `StoreResult` stores once, so every operand has been read when the local is written. An operand whose last use is that instruction then does not meet the result, and a phi joins its next value: the loop's `ldloc iv; ldc 1; add; stloc iv` needs no copy on the back edge. Every other result, phis and the edges' copies keep their positions, the linear scan still never gives a result an operand's local outside such a class, and functions of 512 values or fewer keep a local per value.

```
cmp DWORD PTR [rbp-0x280],0x1 ; jg

```

`new_solver`'s IL goes from 433,229 to 421,474 bytes (local references 47,046 to 45,040, locals unchanged).

## Correctness

`tests/induction-copies.sh` (core) generates a loop with an index counting up, a counter counting down and a body of 600 values, past the 512 at which a function shares locals; it must print what its native build prints in both modes, and the IL of its function must have no load of one local stored into another (`LlvmNet.Checks il-opcodes --locals`, which writes each `ldloc` and `stloc` with its local's index): before PF-29 its back edge copied the index and the counter, now nothing. The core gate passed 109 of 109 tests.

## What remains

- `digits_2` is 1.3 to 1.4 times native's time. Its counters and indexes stay in stack slots where native code keeps most in registers, and the row offset is computed with an `imul` and stored on every iteration where native code steps a pointer (LLVM's loop strength reduction, which runs in the native backend and not before llvmnet's translation).
- `new_solver` (2.6 times) spends most of its difference on stack slots, in RyuJIT's register allocation of a method of 7,878 blocks; raising the tracked-local limit does not help.
