# mimalloc port for the dotnet64-v2 ABI

This directory holds the llvmnet port of mimalloc 3.6.1, the allocator of the portable C library (PF-25, decided by the owner on 2026-11-07). `scripts/build-portable-mimalloc.sh` copies the pinned upstream source, applies `llvmnet.patch`, overlays `src` and `llvmnet-libc.c` from here, and compiles all of mimalloc as one translation unit with llvmnet into one bitcode object, `mimalloc.o`, which it adds to the sysroot's `libc.a`. `scripts/build-portable-libc.sh` leaves musl's own allocator out of `libc.a`: mallocng (`src/malloc/mallocng/`) and the files of `src/malloc/` that define `malloc`, `calloc`, `realloc`, `free` and their internal names (`calloc.c`, `free.c`, `libc_calloc.c`, `lite_malloc.c`, `realloc.c`, `replaced.c`). `scripts/build-sysroot.sh` runs both, after which every portable program that allocates links mimalloc.

- `llvmnet.patch` adds one case to `src/prim/prim.c`: portable programs (`__LLVMNET_PORTABLE__`) include the primitive layer `src/prim/llvmnet/prim.c` instead of the Unix one. It also leaves out an empty `asm` statement on the allocation fast path (`src/alloc/alloc.c`) whose only purpose is to make GCC load a field before a test: llvmnet translates an `asm` without instructions to a full memory barrier, which cost every `malloc` a fence (in omnetpp 19% of `mi_malloc`'s samples).
- `src/prim/llvmnet/prim.c` is that layer. Memory comes only from two host entry points over .NET's `NativeMemory` ([docs/dev/host-abi.md](../../docs/dev/host-abi.md)): `__llvmnet_memory_allocate(size, alignment)` returns zeroed memory with the requested alignment, from `calloc`, which leaves large blocks to the system's lazily zeroed pages, and `__llvmnet_memory_free(address)` releases such a block whole. Nothing calls `mmap`, `munmap`, `madvise` or `mprotect`, not even the host's emulation of them, so the allocator runs wherever .NET runs. A block is usable as soon as it is allocated: the layer reports no virtual reservation and no partial free, and commit, decommit, reset, reuse and guard pages only report success; a decommitted range keeps its contents, and mimalloc's commit bookkeeping does not assume otherwise. Purging, which would decommit or reset ranges that cannot go back to .NET, is off by default (`purge_delay` -1). The clock (`clock_gettime`), random bytes (`getentropy`), the environment (`getenv`, for the `MIMALLOC_*` options), error output (`write` to descriptor 2) and process statistics (`getrusage`) go through musl, which reaches the host through its system calls. Allocation failures set `errno` to `ENOMEM` (or `EINVAL`), as musl's allocator does; mimalloc's default handler sets it only when it is still 0. Huge OS pages and NUMA nodes are not available.
- Threads are musl's pthreads on managed threads. The thread id mimalloc compares on every `free` is the address of a thread-local variable, mimalloc's portable fallback, taken because llvmnet does not define `__x86_64__` and mimalloc therefore reads no thread-pointer register: a .NET thread that runs translated code without musl thread state (a signal handler's thread) still gets a heap of its own. Thread exit is detected with a pthread key whose destructor calls `_mi_thread_done`, as on Unix: musl runs it when a thread returns or calls `pthread_exit`, before or after the program's own key destructors and `thread_local` destructors, which may still allocate and free; mimalloc abandons the thread's pages to other threads, and frees from other threads, also after the owner has exited, go to the page's thread-free list. A thread that a host library started and that calls the program back through a native extension (NX-08) runs no key destructors at exit, so its heap is never released and its pages stay with it. `fork` stays `ENOSYS`, and mimalloc registers no fork handler.
- `llvmnet-libc.c` is the translation unit: mimalloc's single-file `src/static.c` and the allocation functions of musl's `libc.a`. `malloc`, `realloc`, `free`, `malloc_usable_size` and musl's internal `__libc_malloc`, `__libc_realloc` and `__libc_free` are aliases of mimalloc's functions. `calloc` (and `__libc_calloc`) and `aligned_alloc` keep musl's argument checks, because mimalloc's release build returns null without `errno` for a `calloc` size that overflows, and fails a zero alignment, which musl accepts. `__malloc_donate`, through which musl's dynamic linker gives the allocator unused ends of loaded segments, does nothing: portable programs load none. musl's `posix_memalign`, `memalign`, `valloc` and `reallocarray` stay and call `aligned_alloc` and `realloc`, and C++'s `operator new` and `operator delete` stay libc++abi's, which call `malloc` and `free`, so the whole family, musl's internal callers (locale, `atexit`, time zones, `pthread_atfork`, `sem_open`, `dlerror`, `aio`) and C++ allocate from mimalloc. The C names are weak definitions: in musl each is an archive member of its own, which a program that defines its own `malloc`, `calloc` or `free` keeps out of its link, and in one object only a weak definition gives way to the program's (libc-test's `flockfile-list` does this). After compiling, the build script makes every other symbol of the object internal (`opt -passes=internalize,globaldce`), so mimalloc's own names (`mi_malloc`, `_mi_options_init`) cannot clash with a program that defines them or links a mimalloc of its own, and the parts of mimalloc's API that the C names do not reach drop out of the object.
- The build is mimalloc's release configuration (`NDEBUG`) with `MI_LIBC_MUSL`, without the heap profiler (`MI_PROFILE=0`, which writes its files with stdio), without the fork handler (`MI_NO_PTHREAD_ATFORK`) and without mimalloc's weak `std::get_new_handler` (`MI_NO_CXX_NEW_HANDLER`), which would compete with libc++'s. `free` finds a block's page through mimalloc's page map (`MI_FREE_USE_PAGEMAP`) instead of page metadata at 256 MiB-aligned addresses, mimalloc's default: an `mmap` system trims an over-allocation to that alignment, but a block from the host is freed only whole, so every arena would occupy twice its size, and the direct allocation mimalloc falls back to when no arena fits would need the same alignment. The page map was also faster: 20 million `malloc`/`free` pairs took 0.43 s against 0.53 s as NativeAOT. `__x86_64` is undefined while compiling, so that mimalloc assumes no processor: it would otherwise size its page map for x86-64's 47-bit user addresses, while portable images also run on hosts whose .NET hands out 48-bit addresses (Linux ARM64). Like the other runtime libraries it is compiled at `-O2` without the vectorizers; `-O3` measured the same.

Differences from musl's allocator that programs can see: `malloc_usable_size` returns the size of mimalloc's block, at least the size asked for, where mallocng returns exactly that size (glibc also returns more); memory freed by the program stays with the allocator for reuse, since none of it can be returned to .NET except whole blocks; and the first allocation takes a 256 MiB arena, whose pages the system provides only as they are touched. The host counts the allocator's blocks against the same limits as mappings (`RLIMIT_AS`, `RLIMIT_DATA` and the memory .NET reports), so allocation fails with `ENOMEM` where `mmap` would; when an arena no longer fits, mimalloc takes smaller arenas and then single pages, so a program can still allocate most of a low limit (6 MiB of 16, 837 MiB of 1,000 in 100 KB blocks, against mallocng's 15 and 976 MiB). `MIMALLOC_VERBOSE=1` and `MIMALLOC_SHOW_STATS=1` print mimalloc's options and statistics on standard error, as with a native mimalloc.
